# 首页用户排名逻辑 · 实现逻辑与架构设计

> 本文档梳理首页「当前用户今日排名」的排序口径、调用链路、架构设计与性能策略。
> 早期版本仅做逆向分析并指出性能问题；现已按"只展示当前用户名次 + 总人数、无榜单、无前 100 限制、不取昵称"的诉求完成重构，本文档同步更新实现逻辑。

---

## 1. 功能概述

首页（`pages/index/index`）顶部展示当前登录用户的**今日排名**，排序口径为：

- 排序键：`user_stats.dailyTotalDuration`（当日累计冥想时长，单位分钟）
- 排序方向：降序（时长越长排名越靠前）
- 展示内容：**仅**当前用户的名次（`currentUserRank`）与打卡总人数（`totalUsers`）
- **不展示榜单列表、不限制前 100 名、不展示其他用户昵称**
- 当用户本人无任何打卡记录（`user_stats` 无对应文档）时，展示「暂无排名」

该排名**每次进入首页时实时计算**，不读取预生成的快照（快照链路已整体废弃）。

名次语义说明：使用 `count(dailyTotalDuration > 当前用户时长) + 1` 计算名次，因此**同为该时长的并列用户会获得相同名次**，符合常理。

## 2. 架构设计

### 2.1 设计取舍

| 诉求 | 旧实现 | 新实现 |
|------|--------|--------|
| 展示完整榜单 | 取前 100 + 全量拉取 | **不展示榜单**，仅返回当前用户名次 |
| 前 100 名限制 | 硬性 `limit(100)`，>100 显示「未上排行榜」 | **无前 100 限制**，真实名次任意用户量准确 |
| 昵称补全 | 前 100 名逐条查 `user_profiles`（N+1） | **不取昵称**，彻底消除 N+1 |
| 名次计算 | 全量 `orderBy + get` 后 `findIndex`（>1000 越界） | 2 次 `count` 聚合，不受 1000 条限制 |
| 总人数 | = 前 100 查询结果长度（最多 100） | `collection.count()`，真实总数 |
| 预生成快照 | 定时器每 6h 写 `ranking_snapshots`（从未读取） | **删除快照链路**，仅保留实时计算 |

### 2.2 性能模型

重构后的云函数每次调用的 DB 交互为**固定 3 次**，与设计用户量无关：

1. `get()`：查当前用户 `user_stats` 的 `dailyTotalDuration`（加 `.field` 仅取必要字段）
2. `count()`：统计 `dailyTotalDuration > 当前用户时长` 的人数 → 名次 = 该值 + 1
3. `count()`：统计 `user_stats` 总文档数 → 真实总人数

相比旧实现最坏 ~102 次 RPC（1 次 orderBy+limit100 + 最多 100 次昵称查询 + 1 次全量拉取）以及全表扫描排序，固定 3 次聚合查询彻底消除了随用户量线性恶化的主因。

### 2.3 前端缓存策略

首页排名通过 `getCachedCloudRanking()` 走本地缓存：

- 缓存键：`cloud_ranking_cache`
- 有效期：**2 分钟**（原 6 小时，过久导致打卡后名次长时间不刷新；2 分钟既挡住高频 `onShow` 的重复请求，又保证打卡后较快看到新名次）
- 命中且未过期 → 直接 `resolve(cache.data)`，不触发云函数
- 仅在 `onShow`、登录成功、`refreshPageData` 三处调用 `loadRanking()`

## 3. 调用链路（前端 → 云函数）

```
pages/index/index.js
  ├─ onShow / 登录成功 / refreshPageData
  │     └─ loadRanking()                         → 仅消费 currentUserRank / totalUsers / showRankUnit
  │           └─ getCachedCloudRanking()         → 本地缓存命中(2min)则直接返回
  │                 └─ wx.cloud.callFunction({
  │                       type: 'getRankingSnapshot',
  │                       rankingType: 'daily'
  │                     })  ──►  meditationManager 云函数

meditationManager/index.js
  ├─ main dispatch: case "getRankingSnapshot"
  │     └─ getRankingSnapshot(event)   → 调用 getRankings() 实时计算
  │
  └─ getRankings(period)               ← 真正干活的轻量聚合逻辑（固定 3 次查询）
```

废弃路径（已删除）：
- `getRankings` 的 `type:'getRankings'` dispatch case（原 `cloudApi.getRankings` 封装，前端 0 引用）
- `generateRankingSnapshot`（原定时器每 6h 写 `ranking_snapshots`）
- `initRankingSnapshot`（向 `ranking_snapshots` 插入 `test_user_1/2` 测试数据）
- `updateRankings` 及其 `updateDailyRanking/updateMonthlyRanking/updateTotalRanking`（每次打卡向 legacy `rankings` 集合的无效写入）
- `meditationManager/config.json` 中的 `rankingSnapshotTrigger` 定时器

## 4. 实现逻辑详解（`getRankings`）

```js
// 入参 period（默认 'daily'），通过 wxContext 取当前用户 OPENID
async function getRankings(period) {
  const wxContext = cloud.getWXContext();
  const currentUserOpenId = wxContext.OPENID;

  // 1) 查当前用户当日总时长（仅取必要字段）
  const userStatRes = await db.collection("user_stats")
    .where({ _openid: currentUserOpenId })
    .field({ dailyTotalDuration: true })
    .get();

  // 无任何打卡统计 → 暂无排名
  if (userStatRes.data.length === 0) {
    const total = await db.collection("user_stats").count();
    return { success: true, data: {
      type: period, period: getBusinessDate(),
      currentUserOpenId, currentUserRank: 0, hasRanking: false,
      totalUsers: total.total
    }};
  }

  const userDuration = userStatRes.data[0].dailyTotalDuration || 0;

  // 2) 名次 = 时长严格大于当前用户的人数 + 1（count 聚合不受 1000 条限制）
  const higherCount = await db.collection("user_stats")
    .where({ dailyTotalDuration: db.command.gt(userDuration) })
    .count();

  // 3) 真实总打卡用户数
  const totalCount = await db.collection("user_stats").count();

  return { success: true, data: {
    type: period, period: getBusinessDate(),
    currentUserOpenId,
    currentUserRank: higherCount.total + 1, hasRanking: true,
    totalUsers: totalCount.total
  }};
}
```

前端 `loadRanking` 依据 `hasRanking` 渲染：
- `hasRanking === true`：`currentUserRank` 显示真实名次 + 「名」单位（`showRankUnit = true`）
- `hasRanking === false`：显示「暂无排名」（`showRankUnit = false`）

返回结构（精简，不含榜单数组）：
```js
{ success, data: { type, period, currentUserOpenId, currentUserRank, hasRanking, totalUsers } }
```

## 6. 残留风险与人工操作步骤

### R-索引（需人工）
`where({ dailyTotalDuration: _.gt(x) }).count()` 的范围条件在 `dailyTotalDuration` 上有索引时可避免全表扫描。微信云开发**无法通过 wx-server-sdk 建索引**，需手动在云开发控制台操作：

> 云开发控制台 → 数据库 → `user_stats` 集合 → 索引管理 → 新建单字段索引：
> 字段 `dailyTotalDuration`，排序 `降序`（方向对 count 范围查询影响有限，建单字段索引即可）。

### R-未登录/弱网降级
`onShow` 仍会触发一次云函数（缓存未命中时）。弱网下 `getCachedCloudRanking` reject 后，`loadRanking` 走 `fail` 分支显示「暂无排名 / 加载失败」，不影响首页其余功能。

### R-并列名次
同为该时长的用户名次相同（均为"大于者数+1"），为预期语义，非缺陷。

## 8. 结论

首页排名已从"全表扫描 + N+1 + 全量拉取 + 死代码快照"重构为"固定 3 次聚合查询 + 2 分钟前端缓存"的轻量架构，彻底消除了随用户量线性恶化的主因，并在任意用户量下保证名次与总人数的准确性。仍建议按 §6 在云开发控制台为 `user_stats.dailyTotalDuration` 建立索引以进一步降低 DB 扫描成本。云函数改动需在微信开发者工具中"上传并部署"后方可生效。
