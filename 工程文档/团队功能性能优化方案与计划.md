# 团队功能性能优化方案与计划（架构级）

> 生成日期：2026-08-03
> 配套文档：《团队功能逆向分析与性能诊断.md》
> 目标：从架构层面整体解决团队功能性能问题，而非局部打补丁。

---

## 一、问题定性（架构视角）

团队功能当前的性能问题，本质是**"团队维度没有独立的数据视图，所有统计都实时回查个人原始表 `meditation_records`，且回查方式是逐成员串行 + 正则扫描"**。

架构缺陷分三层：

| 层级 | 缺陷 | 后果 |
|------|------|------|
| **数据模型层** | `meditation_records` 只有 `_openid`，无 `teamId`；无团队维度的预聚合集合 | 任何团队统计都必须"按成员逐个回表"，无法 O(1) 聚合 |
| **后端服务层** | `getTeamMembersCheckinData` 用 `for` 循环串行查 + `db.RegExp` 正则匹配 `date`；`getTeamMeditationRecords` case 缺失 | 每次团队详情 = N×2 次串行 DB 查询 + 全表正则扫描 |
| **前端调用层** | 首屏 `loadTeamData` 同时拉"成员列表打卡"+"本周动态"+详情；"本周动态"因 case 缺失返回空；无缓存、无并发、无分页 | 首屏卡顿；动态时间线永久空白 |

> 注：经代码核实，前端对 `getTeamMembersCheckinData` 的取数路径（`memberCheckinData[member.openid]`）**是正确的**，并非之前怀疑的"错位丢弃"。真正的功能断点在 `getDirectMemberWeekActivities` 调用的 `getTeamMeditationRecords`（云函数无此 case，返回空数组 `[]`，"本周练习动态"时间线恒为空）。

## 二、目标架构

```
打卡写入 meditation_records(_openid, date, duration, timestamp...)
        │  （新增）异步写团队聚合
        ▼
team_checkins(teamId, openid, date, duration, timestamp)   ← 团队维度原始记录（带索引）
        │  （定时/写时）聚合
        ▼
team_daily(teamId, date)      ← 团队-日汇总：membersCheckedIn / totalDuration / records[]
team_member_stats(teamId, openid) ← 成员在团队内的月/总打卡（避免每次回查个人表）
        │
        ▼
teamManager 提供聚合查询接口（1 次调用返回全员/全动态）
        │
        ▼
前端一次性渲染 + 本地缓存 + 增量刷新
```

**核心思想**：把"团队维度"作为一等公民建模，用空间（多存一张聚合表）换时间（O(1) 查询）。

## 三、分阶段实施计划

### 阶段 0：止血（1 天，低风险，立刻消除卡顿与空白）

**目标**：不引入新集合，先让现有接口不卡、功能不缺。

1. **补 `getTeamMeditationRecords` 云函数 case**（修复"本周动态"空白）
   - 实现：接收 `teamId` + `weekStart/weekEnd`，查 `meditation_records` 时按 `team_members` 拿到成员 openid 列表，用 `db.command.in(memberOpenids)` **单次 `where` + 范围查询**返回本周全部记录。
   - 关键：用 `date: db.command.gte(weekStartStr).and(lte(weekEndStr))` 范围匹配，**不要正则**；`in` 数组查询一次搞定，避免逐成员。

2. **`getTeamMembersCheckinData` 改为并发 + 范围查询**
   - `for` 循环内 `await` → 改成 `await Promise.all(memberOpenids.map(o => queryOne(o)))`。
   - `db.RegExp({regexp: '^2026-08'})` → 改为 `date: db.command.gte('2026-08-01').and(db.command.lte('2026-08-31'))` 字符串范围（对 `YYYY-MM-DD` 有序，可走索引）。
   - 月度 `count` 同理可并行。

3. **前端并发 + 缓存**
   - `loadTeamData` 中的多个 `await` 调用用 `Promise.all` 并发。
   - "本周动态"调用改为消费真实返回（阶段 0 第 1 步已修 case）。

**阶段 0 验收**：20 人团队详情首屏云函数调用从 ~40 次降到 ≤3 次；"本周动态"有数据。

---

### 阶段 1：建模（2-3 天，中等风险，结构性优化）

**目标**：引入团队维度聚合集合，彻底摆脱"逐成员回查个人表"。

1. **新增集合 `team_checkins`**
   - 在 `recordMeditation`（meditationManager）打卡成功后，**异步写一条 `team_checkins`**（`teamId` 来自 `team_members` 当前所属团队，`openid`, `date`, `duration`, `timestamp`）。
   - 用 `autoCreateCollections` / `create_team_collections.js` 登记 schema。

2. **新增集合 `team_daily`（团队-日汇总）**
   - 每日 4 点定时任务（复用现有 `bijingSync` 的定时触发机制或新建 `teamStats` 云函数 `TIMER`），扫描 `team_checkins` 按 `(teamId, date)` 聚合：`membersCheckedIn`、`totalDuration`、`records`。
   - 团队详情的"今日/本月打卡"直接读 `team_daily`，O(1)。

3. **新增 `team_member_stats`（成员团队内统计）**
   - 字段：`teamId`, `openid`, `monthlyCount`, `monthlyDuration`, `totalCount`。
   - 写时 `db.command.inc` 增量更新（对齐 `user_stats` 的 inc 模式）。
   - 成员列表的 `monthlyCount/totalCount` 直接读此表，不再回查 `meditation_records`。

4. **新增索引**
   - `meditation_records`：`(_openid, date)`
   - `team_checkins`：`(teamId, date)`、`(teamId, openid)`

**阶段 1 验收**：团队详情首屏云函数调用 = 1 次（`getTeamDaily`）；成员列表数据来自聚合表。

---

### 阶段 2：体验（2 天，低风险，前端增强）

**目标**：缓存、分页、骨架屏，应对大规模团队。

1. **前端缓存策略**
   - `team_daily` 结果缓存到 `storage`，`onShow` 仅刷新"今天"增量（对比 `lastRefreshDate`）。
   - "本周动态"分页加载（每次 20 条，`start` 游标）。

2. **渲染优化**
   - 成员多时虚拟列表 / 分块 `setData`（避免一次性 set 大数组）。
   - 加载态骨架屏，`getTeamMembersCheckinData` 期间不阻塞列表渲染。

3. **降级容错**
   - 聚合表未就绪时，降级到阶段 0 的 `in` 查询（保证功能不退化）。

## 四、关键设计决策

### D1：`team_checkins` 是"写时双写"还是"定时回扫"？
- **推荐写时双写**：在 `meditationManager.recordMeditation` 成功后，用 `db.collection('team_members').where({openid}).get()` 查所属团队，异步 `add` 到 `team_checkins`。延迟可接受（团队详情读的是 `team_daily` 聚合表，T+1 由定时任务修正）。
- 定时回扫仅作为兜底（修复历史数据 / 校准），不作为主路径。

### D2：聚合时机
- `team_daily` 用**每日 4 点定时聚合** + **写时增量 inc** 双保险（对齐 `user_stats` 既有模式）。首屏读 `team_daily` 永远 O(1)。

### D3：`getTeamMeditationRecords` 与 `getTeamMembersCheckinData` 是否保留？
- 阶段 0 保留并修复（止血）；阶段 1 后，`teamDetails` 改为优先读 `team_daily`/`team_member_stats`，旧接口仅作降级。

### D4：索引
- `meditation_records` 当前无 `(openid, date)` 复合索引 → 阶段 1 必须建。微信云开发索引需在控制台或 `config.json` 声明（注意：项目曾出现 `config.json` 触发器未生效的问题，索引也建议控制台手动确认）。

## 五、工作量与风险

| 阶段 | 改动文件 | 工作量 | 风险 | 依赖 |
|------|----------|--------|------|------|
| 0 止血 | `teamManager/index.js`（2 个函数）+ `teamDetails.js`（并发/缓存） | 1 天 | 低 | 无 |
| 1 建模 | 新增 2 集合 + `meditationManager.recordMeditation` 双写 + 定时聚合云函数 + 索引 | 2-3 天 | 中（涉及写路径） | 需建集合/索引 |
| 2 体验 | `teamDetails.js` / `team.wxml` | 2 天 | 低 | 阶段 1 |

**建议顺序**：先阶段 0（立刻见效、风险低），再阶段 1（根治），最后阶段 2（规模化）。

---

## 六、验证指标

- **调用次数**：云开发控制台 `teamManager` 监控，团队详情首屏调用次数：阶段 0 后 ≤3，阶段 1 后 =1。
- **耗时**：首屏 `loadTeamData` 总耗时（前端测）：20 人团队 < 800ms。
- **功能完整**："本周练习动态"时间线有数据；成员月/总打卡数正确。
- **回归**：打卡主链路（`recordMeditation`）不受影响；`user_stats` 不受影响。

## 七、待确认事项（开工前）

1. 一个用户是否**只属于一个团队**？若支持多团队，`team_checkins` 需 `teamId` 数组、双写需遍历。
2. 团队规模上限预期？（决定是否需要阶段 2 虚拟列表）
3. 是否允许引入"写时双写"改动 `meditationManager`（主程序核心写路径）？若不允许，可改为纯定时回扫 `meditation_records` 重建 `team_checkins`（牺牲实时性保安全）。
