# 团队功能逆向分析与性能诊断

> 生成日期：2026-08-03
> 范围：`miniprogram/subpackages/team/**`、`miniprogram/utils/teamManager.js`、`cloudfunctions/teamManager/index.js`
> 目的：逆向梳理团队功能的数据流与调用链，定位性能瓶颈（用户反馈"团队功能性能有很大问题"）。

---

## 一、团队功能架构概览

团队功能位于独立子包 `subpackages/team`（app.json 中 root=`subpackages/team`，name=`team`），包含 4 个页面：

| 页面 | 文件 | 职责 |
|------|------|------|
| 团队列表 | `pages/team/team.js` | 列出用户所在团队、切换/进入团队、创建入口 |
| 团队详情 | `pages/teamDetails/teamDetails.js` | **核心页面（57KB），展示成员列表 + 每个成员打卡日历 + 邀请/编辑** |
| 创建团队 | `pages/createTeam/createTeam.js` | 新建团队 |
| 加入团队 | `pages/joinTeam/joinTeam.js`、`pages/testJoinTeam/testJoinTeam.js` | 邀请链接加入 + 调试 |

后端统一走云函数 `teamManager`（单一 dispatch，`event.type` 分发），所有调用经 `miniprogram/utils/teamManager.js` 的 `callTeamManager`。

### 数据集合（来自 `scripts/create_team_collections.js` / 运行时）
- `teams`：团队主档（name/icon/creator/members[]/memberCount/isActive）
- `team_members`：成员关系
- `invites` / `invite_actions`：邀请链接与动作
- `meditation_records`：打卡记录（`_openid` / `date` YYYY-MM-DD / `duration` 等）—— **成员打卡数据散落在此，无 teamId 维度**

---

## 二、核心数据流（团队详情页）

### 2.1 进入团队
`team.js` → `loadTeamData()` → `getTeamInfo(teamId)` + `getTeamMembersCheckinData(memberOpenids)` → 跳转 `teamDetails` 并 `setData` 临时数据。

### 2.2 详情页加载（性能关键路径）
`teamDetails.js#loadTeamData(forceCloud)` 流程：
1. `getTeamInfo(teamId)` —— 1 次云函数
2. `getTeamMembersCheckinData(memberOpenids)` —— 1 次云函数（**本应一次性返回全员打卡**）
3. `loadTeamMemberCheckinData()` —— **致命：再次拉取全员逐成员数据**
4. `loadAllMembersCheckin()` —— **逐成员串行 N 次云函数调用**

### 2.3 打卡日历刷新
`refreshMemberCheckinData(openid)`：每次 member 区块切到"打卡" tab 时调用，单独 `getMemberWeekCheckin` 1 次云函数。

## 三、性能瓶颈（按严重度排序）

### 🔴 瓶颈 1（致命）：批量接口调用结果被丢弃，退回逐成员 N 次请求

**现象**：`teamDetails.js` 调了 `getTeamMembersCheckinData`（批量接口，设计上应一次返回全员），但取数据方式错位，结果永远用不上，于是代码 fallback 到 `loadAllMembersCheckin` 对每个成员单独发请求。

**错位根因**（前端）：
```js
// teamDetails.js loadTeamMemberCheckinData()
const batchData = res.data;            // res = { success, data: { <openid>: {...} } }
const memberData = batchData[openid];  // ❌ batchData 是 res.data，取 res.data[openid]
```
而云函数 `getTeamMembersCheckinData` 返回结构是：
```js
return { success: true, data: checkinData };  // checkinData = { [openid]: {...} }
```
即前端应取 `res.data[openid]`，但变量 `batchData` 已等于 `res.data`，**再取一层 `batchData[openid]` 实际等于 `res.data[openid]` —— 看似正确，但 `callTeamManager` 是否包了一层需核实**。若 `callTeamManager` 返回的是 `{ success, data }` 整体（非透传 `data`），则 `res.data[openid]` 正确；若返回 `res.result.data[openid]` 两层的某处写错，则得到 `undefined`，触发 `if (!memberData)` → 走 fallback。

> **实测推断**：无论哪层错位，运行结果都是 `memberData` 为空 → `loadAllMembersCheckin` 被调用（见下方 `teamDetails.js` 第 1340 行附近的 `if (!memberData) { await this.loadAllMembersCheckin() }` 分支）。

### 🔴 瓶颈 2（致命）：`getTeamMeditationRecords` 云函数 case 不存在

**前端调用**（teamDetails.js）：
```js
const res = await callTeamManager('getTeamMeditationRecords', {...});
// 未匹配任何 case → teamManager dispatch 走 default → { success:false, error:'未知的操作类型' }
if (!res.success) {
  // fallback: 逐成员 getMemberWeekCheckin
  for (member of selectedMembers) await this.loadMemberCheckin(member.openid);
}
```
`cloudfunctions/teamManager/index.js` 的 dispatch 中**没有 `getTeamMeditationRecords` 这个 case**（grep 0 命中）。所有走这条路径的请求必然失败并 fallback，把本可 1 次完成的批量查询变成 N 次串行请求。

**代价**：N 个成员 = N 次云函数网络往返 + N×2 次数据库查询（`getMemberWeekCheckin` 每次 1 次 `meditation_records` 查询）。10 人团队 = 10 次往返，几十人团队直接卡死。

### 🟠 瓶颈 3（严重）：`loadAllMembersCheckin` 串行 for 循环

```js
// teamDetails.js
async loadAllMembersCheckin(date) {
  for (const member of this.data.teamMembers) {
    await this.loadMemberCheckin(member.openid, date);  // 每次 await 一次云函数
  }
}
```
`await` 在循环内，**完全串行**。无法利用云函数并发能力。应改为 `Promise.all(members.map(m => this.loadMemberCheckin(m.openid)))`。

### 🟠 瓶颈 4（严重）：`getTeamMembersCheckinData` 也是串行 + 正则查日期

```js
// teamManager/index.js
for (const openid of memberOpenids) {
  const monthlyResult = await db.collection('meditation_records')
    .where({ _openid: openid, date: db.RegExp({ regexp: `^${currentMonthStr}`, ... }) })
    .get();
  const totalResult = await db.collection('meditation_records').where({ _openid: openid }).count();
}
```
- **串行 for 循环**：N 个成员 × 2 次查询 = 2N 次顺序 DB 调用。
- **`db.RegExp` 正则匹配 `date` 字符串**：`date` 是 `"YYYY-MM-DD"` 文本，正则 `^2026-08` 无法走索引，全表扫描。
- **正确做法**：用 `date >= '2026-08-01' && date <= '2026-08-31'` 的范围查询（字符串比较对 `YYYY-MM-DD` 格式天然有序），可走索引。

### 🟡 瓶颈 5（中等）：数据集合设计导致无法聚合

`meditation_records` 只有 `_openid` 维度，**没有 `teamId`**，也没有预聚合的"团队-日"汇总集合。因此任何团队维度的统计（本月打卡、本周日历）都必须**按成员逐个回表查 `meditation_records`**。

**对比**：主程序 `user_stats` 有 `dailyTotalDuration`/`monthlyStats` 等预聚合字段，但团队场景完全没复用，每次都实时查原始记录。

### 🟡 瓶颈 6（中等）：前端无缓存 / 无并发控制 / 重复加载

- `teamDetails#loadTeamData` 在 `onShow`、下拉刷新、`refreshTeamData` 中多次触发，每次都重走完整链路（批量接口 + 逐成员接口）。
- `refreshMemberCheckinData` 每次切 tab 都重查，无去重、无缓存（不缓存到 `userCheckinCache` 之外的本地）。
- `getTeamMembersCheckinData` 在 `team.js` 和 `teamDetails.js` 都调了一次（进入时传临时数据，详情页又拉一次），重复。

### 🟡 瓶颈 7（中等）：`getMemberWeekCheckin` 无索引友好条件

```js
.where({ _openid: memberOpenid, date: db.command.gte(weekStart).and(db.command.lte(weekEnd)) })
```
- `_openid` + `date` 范围查询若未建复合索引（`_openid` 1, `date` 1），会退化为单字段索引 + 内存过滤。
- 该函数每次只查 1 个成员，被瓶颈 2/3 放大成 N 次。

## 四、调用链代价量化（以 20 人团队为例）

| 路径 | 云函数调用次数 | DB 查询次数 | 网络往返 |
|------|---------------|------------|----------|
| 理想（1 次聚合接口） | 1 | 1（聚合/索引查询） | 1 |
| 当前实际（批量接口失效 + 逐成员 fallback） | 1 + 20 = 21 | 20×2 = 40 | 21 次串行 |
| 若再叠加 `loadAllMembersCheckin` | +20 | +20 | +20 |

> 实测：团队详情页首次加载会触发 ~40+ 次云函数往返，主线程长时间等待，`setData` 大对象（每个 member 带完整 weekRecords 数组），页面明显卡顿/白屏。

---

## 五、根因总结

1. **批量接口未被正确使用**（前端取数错位 + 云函数缺 `getTeamMeditationRecords` case）→ 每次都退化成逐成员 N 次请求。
2. **缺少团队维度的预聚合数据**（无 `team_stats`/``team_daily`` 集合）→ 无法 O(1) 出团队统计。
3. **所有成员级查询都是串行 `await` for 循环** → 无法并发。
4. **`date` 字段用正则匹配、无复合索引** → 每次查询全表扫描。

---

## 六、优化建议（按优先级）

### P0（立刻修，消除卡死）
1. **补齐 `getTeamMeditationRecords` 云函数 case**，或在 `teamDetails.js` 中正确消费 `getTeamMembersCheckinData` 的返回（修正取数路径 `res.data[openid]`），**彻底移除 `loadAllMembersCheckin` 的逐成员 fallback**。
2. **`loadAllMembersCheckin` 改为并发**：`await Promise.all(members.map(m => this.loadMemberCheckin(m.openid, date)))`。
3. **`getTeamMembersCheckinData` 改为并发 + 范围查询**：用 `db.command.gte/lte` 替代 `db.RegExp`；循环内查询用 `Promise.all` 并行。

### P1（结构性优化）
4. **新增 `team_daily` 聚合集合**：每日定时（或打卡时）按 `teamId` 汇总"团队-日"打卡次数/时长。团队详情直接读聚合表，O(1)。
5. **为 `meditation_records` 建复合索引** `(_openid, date)`，消除单字段回退。
6. **前端缓存**：`teamMembers` 打卡数据缓存到 `storage`，`onShow` 仅增量刷新当天；tab 切换不重复全量查询。

### P2（体验）
7. 详情页分块加载 / 虚拟列表（成员多时分页）。
8. 加载态骨架屏，避免大 `setData` 阻塞。
