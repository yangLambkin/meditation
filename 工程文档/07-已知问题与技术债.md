# 07 - 已知问题与技术债

> 逆向自代码与 `CODEBUDDY.md`，汇总当前明确的缺陷、冗余与待办。涉及改动前请先评估影响面。

---

## 1. 数据字段问题

### 1.1 情绪字段丢失（emotion / 情绪）
- `meditation_records` **没有**情绪（emotion）字段，仅保留 `rating` 评分。
- 若产品需要"心情/情绪"维度，需在 `meditationManager.recordMeditation` 与数据模型同步补字段，并兼容历史数据（历史记录缺省处理）。

### 1.2 rating 类型不一致
- 运行时 `recordMeditation` 将 `rating` 作为**数字**处理（`data.rating || 0`）。
- `create_collections_consistent.js` 的参考 schema 未与运行代码对齐（评分类型/范围未形成统一约束）。
- 建议：明确 `rating` 的取值范围与类型，并在前后端校验，避免字符串/数字混用。

### 1.3 experience 类型不一致
- 运行时 `meditation_records.experience` 为 **数组**（体验记录 id 列表）。
- `create_collections_consistent.js` 定义为 **string**（遗留）。
- 新代码一律写数组；`updateMeditationRecord` 已做单字符串兼容，但参考 schema 未同步，易误导后续开发。

## 2. 字段命名风格分裂

- 集合内部混用 `camelCase` 与 `snake_case`：
  - `camelCase`：`user_stats`、`meditation_records`、`teamManager` 运行时团队字段（`teamId`/`inviterId`/`openid`/`joinedAt`）。
  - `snake_case`：`experience_records`、`user_mappings`（运行时确有使用的遗留集合，保留）。
- ✅ **团队集合 schema 错配（已修复）**：曾存在 `cloudfunctions/autoCreateCollections/index.js` 的团队/邀请集合用 `team_id`/`inviter_openid`/`user_openid`/`joined_at`，与运行时 `teamManager` 的 `teamId`/`inviterId`/`openid`/`joinedAt` 错位。已于 2026-07-27 将 `autoCreateCollections` 的 `invites`/`team_members`/`invite_actions` 三集合示例数据改为 camelCase，与运行时对齐（见 `8.3`）。
  - 后果：`autoCreateCollections` 建出的集合字段与运行时不符，可能写入/读取错位。
  - 建议：以 `scripts/create_team_collections.js`（camelCase，运行时规范）为准，修正 `autoCreateCollections` 的团队建表定义，或确认运行时字段名。

## 5. 初始化与版本控制债

- `autoCreateCollections` **默认不在 `app.js` 调用**（被注释），新环境集合缺失只能手动触发，易遗漏。
- `appVersion` **硬编码 `1.0.0`**，需要"升级即迁移数据"的语义未真正用起来（仅作缓存恢复触发条件之一）。

## 6. 依赖与构建债

- 根 `node_modules/` 为空；云函数依赖 `wx-server-sdk` 各自安装，无统一锁版本策略，存在跨函数版本漂移风险。
- 云存储 `CLOUD_PREFIX`（长 fileID 前缀）在多处硬编码（`app.js`、`config/images.js`），应统一从 `config/images.js` 的 `CLOUD_PREFIX` 引用，避免分散内联。
- 小程序 npm 依赖须在根目录安装并经「构建 npm」打入 `miniprogram/`，流程易错（见 `06-部署与运维.md`）。

## 8. 已修复项

### 8.1 农历日期由伪算法改为真实 lunar-javascript 包（2026-07-27）
- **原问题**：`miniprogram/utils/lunar.js` 的 `getLunarDate` 采用「硬编码基准日 `2026-02-21 = 丙午年正月初五` + 每月按 30 天循环加减」的伪农历算法，无闰月/大小月/节气，日期会随时间累积错位。
- **选型**：曾试用 `loulin/lunar@2.0.0`，但其为 ESM + `exports` 条件导出 + 无扩展名入口（`dist/index.cjs`），微信「构建 npm」报 `Npm package entry file not found`，不兼容。最终选定 **`lunar-javascript`（6tail，纯 CommonJS，`main: index.js`、无 `exports` 条件导出）** —— 对微信小程序「构建 npm」最友好、社区验证最多、功能最全（闰月/节气/干支/传统节日）。
- **修复**：`utils/lunar.js` 改用 `require('lunar-javascript')` → `Lunar.fromDate(date)` 取真实农历，用 `getYearInGanZhi()`/`getMonthInChinese()`/`getDayInChinese()` 拼接为 `丙午年正月初五`（`getMonthInChinese` 返回不带「月」的中文数字，已补「月」字）。
- **影响面**：对外契约不变（`getLunarDate(Date) → "丙午年正月初五"`），调用方 `pages/daily/daily1.js`、`pages/history/history.js` 无需改动。
- **验证**：多个日期（含原基准日、闰月、端午节）核对正确；`read_lints` 对该文件 0 错误。

### 8.2 农历依赖统一到根 package.json（2026-07-27）
- **配置点**：`project.config.json` 的 `packNpmRelationList.packageJsonPath` 指向根 `./package.json`，故「构建 npm」以根 `package.json` 为准。
- **修复**：根 `package.json` 的 `dependencies` 已声明 `"lunar-javascript": "^1.7.7"`（仓库根 `npm install` 已进入 `node_modules/`）；同步移除不再需要的 `loulin/lunar` 以及 `miniprogram/package.json` 中的 `lunar` 死依赖。
- ✅ **无需 vendoring / 无需改打包配置**：`lunar-javascript` 为纯 CommonJS，标准「工具 → 构建 npm」即可打入 `miniprogram`，`require('lunar-javascript')` 在真机/模拟器均可解析。
- ⚠️ **后续必做**：依赖变更后，在微信开发者工具「工具 → 构建 npm」重新构建（若此前构建失败残留 `miniprogram/miniprogram_npm`，建议先删除再构建）。

### 8.3 团队集合 schema 错配修复（2026-07-27）
- **原问题**：`cloudfunctions/autoCreateCollections/index.js` 的 `invites`/`team_members`/`invite_actions` 三集合示例数据用 snake_case（`team_id`/`inviter_openid`/`user_openid`/`joined_at`/`invite_code`/`invite_url`/`action_type` 等），而运行时 `teamManager` 实际读写 camelCase（`teamId`/`inviterId`/`openid`/`joinedAt` 等），两套命名会让按 snake_case 读取/迁移数据的逻辑错位。
- **判定**：以 `teamManager` 为准（`CODEBUDDY.md` 明确其为运行时字段名 source of truth），camelCase 为规范。
- **修复**：重写了 `autoCreateCollections` 上述三集合的 `sampleData`，字段名全部改为 camelCase，且字段集与 `teamManager` 实际写入一致（同时与 `scripts/create_team_collections.js` 的 canonical 规范一致）。`teams` 集合本就未在 `autoCreateCollections` 中定义，无需改动。
- **影响面**：微信云数据库为 schemaless，示例数据仅用于「建集合后插一条再删除」验证字段可写，不影响既有数据；但消除了命名误导，使 bootstrap 建表与运行时契约一致。
- **验证**：`read_lints` 对该文件 0 错误；grep 确认 `autoCreateCollections` 内已无团队字段的 snake_case 残留（`_openid` 为云数据库系统字段，保留）。
- **附带对齐 canonical 脚本**：同步修正 `scripts/create_team_collections.js` 的 `invite_actions`——将 `targetUser` 改为 `inviteeId`，并补 `inviteTime`/`status`（均为 `teamManager` 的 `recordInviteRelation` 实际写入字段），使 canonical 脚本与运行时完全一致。

## 9. me 页统计计算风险（详见 `08-me页统计计算逻辑与风险.md`）

- **核心问题**：`me` 页四项统计中，`totalMinutes`（当月总分钟）取自**本地缓存** `checkinManager.getCurrentMonthMinutes()`，而 `consecutiveDays`/`currentStreak`/`medals` 取自**云端 `user_stats`**，口径不统一，本地缓存缺失/换设备时 `totalMinutes` 会与云端三项矛盾。
- **已确认风险**：
  - `4.1`（中-高）`totalMinutes` 本地重算 vs 其余云端聚合，存在数据可靠性风险；`me.js#284-316` 有未调用的云端版本死代码。
  - `4.2`（中）云端 `user_stats.monthlyTotalDuration` 跨月不清零（实为累计值），污染"当月"语义。
  - `4.3`（低-中）`recordMeditation` 中 `longestCheckInDays` 在同一天多次打卡时被高估（`stats.currentStreak+1` 不受 `isNewDay` 限制），导致 `me` 页"最长连续天数"虚高。
  - `4.4`–`4.6`（低）`consecutiveDays` 变量命名误导、登录态判定重复实现、`onLoad`+`onShow` 双触发并发。
- **修复方向**：以云端 `user_stats` 为单一可信源，前端只展示；`totalMinutes` 改用 `stats.monthlyStats[当前月].totalDuration`；修复 `longestCheckInDays` 与 `monthlyTotalDuration` 的云函数逻辑。
