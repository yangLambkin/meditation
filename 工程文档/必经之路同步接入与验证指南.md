# 必经之路学号绑定与静坐时长同步 —— 接入与验证指南

> 关联 Plan：`bijing-sync-integration`
> 适用环境：测试环境 `data.bjzl.net.cn`（闭环验证后切生产 `data.bijing.life`）

## 一、整体架构

- 新增独立云函数 `cloudfunctions/bijingSync/`：负责学号校验、时长聚合、对端上报、定时/手动触发。
- 前端 `miniprogram/utils/bijingApi.js`：封装 `bindBijing(sn)`、`checkBijing(sn)`、`getBijingSyncDateDetails(recordDate)`、`syncBijingDate(recordDate)`、`getBijingHeatmap()`。
- `me` 页：「必经之路同步」区块（绑定表单 + 手动同步 + 绑定状态 + 昵称覆盖）。
- 所有外部 HTTPS 调用与 Token 仅在云函数侧，前端不持有任何密钥。
- 热力图通过 `GET /api/openapi/meditation/heatmap?studentNumber=...` 查询，使用同一 `X-Access-Token`。接口清单、迁移说明及发布顺序见 [热力图 OpenAPI 接入说明](../docs/heatmap-openapi.md)。

三个 OpenAPI 请求统一使用 `X-Access-Token: <BIJING_ACCESS_TOKEN>`：学号校验 `GET /api/openapi/users/{studentNumber}`、单学号同步 `POST /api/openapi/meditation/records`、热力图 `GET /api/openapi/meditation/heatmap?studentNumber=...`。同步请求体固定为 `{ studentNumber, recordDate, durationMinutes }`，每次提交一个学号的一天总时长；对端完成写入并返回 `success: true` 后才写本地成功标记并向页面返回结果。自动触发器逐个学号等待完成（含必要重试）后，再处理下一个学号。当前版本不启用异步批次或状态轮询，旧的 `BIJING_BATCH_ENABLED` 配置不再影响调用链。

## 二、关键设计点

### 1. 时长来源「仅云端」
预览与上报共用 `getDayRecords`，只读取当前用户的云端 `meditation_records`。有有效 `timestamp` 的记录按北京时间 **[所选日 02:00，次日 02:00)** 归属，读取全部分页后累加有效数值 `duration`，最后统一四舍五入为整数分钟。

查询同时覆盖时间戳窗口和原 `date`，避免遗漏次日凌晨或旧日期字段不一致的记录。同一文档只返回一次；缺少有效时间戳的历史记录沿用原 `date`，不使用上传时间推测打卡时间。

### 2. 东八区时间口径（已验证无时差）
`meditationManager/index.js#getBusinessDate` 与 `miniprogram/utils/dateUtil.js#getBusinessDate` 使用**完全相同**算法：
用 `new Date(t + 6h)`（北京时间偏移 8 小时，再减去换日偏移 2 小时）后读 `getUTCFullYear/Month/Date()`，**不依赖运行环境时区**。
打卡 `date`、日历、天数、月统计、团队和同步统一使用北京时间 02:00 业务日。例如 9 月 18 日 01:59 的记录属于 `2026-09-17`，02:00 起属于 `2026-09-18`，相邻业务日不重叠。手动补录保留用户选择的业务日期；旧记录有可靠时间戳时重新归属，无可靠时间戳时保留原日期。

### 3. 自动调度与手动同步的窗口
| 入口 | 同步窗口 | 说明 |
|--------|----------|------|
| 凌晨 2 点（定时 `0 0 2 * * * *`） | 每个绑定用户最近一个已结束的同步日 | 正常触发时为昨天 02:00 至今天 02:00；手动提前触发也只取已结束日 |
|「手动同步」| 最近七个已结束同步日中选择一天 | 仅同步选中日期，可补报绑定前的记录 |
| 旧版客户端 `syncPending` | 最近七个已结束同步日 | 兼容旧版调用，忽略 `force`，已同步日期也重新上报 |

> 同步日到次日 02:00 才结束：北京时间 00:00–01:59 可选前天至 8 天前，共 7 个日期；02:00 起可选昨天至 7 天前。前端在打开弹窗和提交时计算日期，云函数再次校验；尚未结束、超出范围及格式错误的日期均拒绝，保证上报日期的统计窗口完整。若云端备份尚未完成、暂时查不到记录（返回 0），此时**不写标记**，可在日期仍处于范围内时重试。

自动同步按同学逐个串行执行，首次尝试失败后最多额外重试 **3 次**，即每人最多尝试 **4 次**；仍失败则记录该同学及业务日期，并继续下一位。整轮返回中 `data.failedUsers` 保留最终失败明细，任何最终失败都会令顶层 `success:false`。所有同步和重试仍在同一次云函数执行里，**不会为每个同学重置平台超时**；单次 HTTP 请求超时 10 秒，4 次请求等待就可能接近 40 秒，另需数据库读写等时间。执行超时可从 60 秒做小规模测试，再按用户数和实际耗时评估；没有断点续跑，整轮超时或当天失败需按日志手动补报，下一天不会自动补前一天遗漏。

新操作参数为 `{ type: 'syncSelectedDate', recordDate: 'YYYY-MM-DD' }`。使用独立操作名，避免旧云函数忽略日期参数后执行历史批量同步。首次和重复同步成功均返回 `data.success`、`data.date` 和 `data.duration`；无可同步时长时返回 `data.skipped` 和 `data.reason`；同步失败返回顶层 `success: false` 和 `error`。

选择日期时先调用只读操作 `{ type: 'getSyncDateDetails', recordDate: 'YYYY-MM-DD' }`，返回当天记录的 `id/timestamp/duration`、次数 `count`、原始总分钟数 `totalDuration`、实际同步的取整分钟数 `syncDuration` 及曾同步成功状态 `alreadySynced`。服务端按当前用户和同步窗口分页读取全部记录，不上报、不写标记；预览与同步使用同一云端数据来源。弹窗展示每次打卡的北京时间与时长、总次数和总分钟数，次日凌晨显示「次日 01:00」，缺失时间显示「时间未记录」。加载中、读取失败或无可同步时长时禁用同步按钮；已同步日期提示「这一天已同步，可再次同步更新记录」，允许继续提交。切换日期及关闭弹窗后忽略旧请求结果，读取失败可重试。

### 4. 同步历史状态 `users.bijingSyncedDates`
结构：`{ "2026-07-30": true, ... }`

**标记的唯一写入时机：对端返回成功（`postMeditationRecord` 成功）后 `markSynced`。**

- `bijingSyncedDates[dateStr]` 仅表示曾经同步成功，供预览展示；不阻止再次同步，也不保证最新补录已上报。
- 对端返回成功 → 写 `true`。
- **云端 `duration <= 0`（当天查不到打卡数据，可能是备份异步未完成） → 不写任何标记**，返回 `skipped` 但留待下次复查。
- 对方接口本身「同号同日幂等覆盖」，自动、手动及旧版批量同步每次都重新汇总最新云端记录并上报。
- 自动与手动可以重复同步同一天；时长有变化时用最新合计覆盖，重复请求不累加时长。再次同步失败会报告本次错误，保留之前的成功状态，允许重试。对端成功而本地尚未确认时遇到网络超时也可能重发，安全性依赖对端维持「同号同日幂等覆盖」契约。

> 历史误标说明：修复前 `duration<=0` 分支也会 `markSynced`，导致"暂时性查不到"被永久标 `true` 并跳过。修复后此路径不再写标记。手动同步仅支持最近七个已结束同步日；更早记录的修复需要单独处理，不能通过日期选择或 `force` 绕过范围限制。

> 02:00 切日升级保留所有已有同步状态；允许范围内的日期再次同步时按新口径重新汇总上报。超出范围的历史数据不会自动重传。如需校正切换前后旧自然日口径的数据，需按相邻日期对账重算，避免只更新某一天后跨日期重复计入凌晨记录。

### 5. `users` 集合新增字段
- `bijingStudentNumber` (string)
- `bijingBound` (bool)
- `bijingBoundAt` (date)
- `bijingSyncedDates` (object)
- 绑定成功时一并更新 `nickName`（见下）

### 6. 绑定后昵称覆盖（补充需求）
`GET /users/{sn}` 成功且 `data.nickname` 非空时：
- 云函数：`users.nickName = 对方昵称`（与写绑定字段同一事务）。
- 前端：`bindBijing` 成功回调里 `wx.setStorageSync('userNickname', 对方昵称)` + `this.setData({userNickname})`，使 `me` 页立即生效。
- 兜底：对方昵称为空则保留原昵称，不阻断绑定。

## 三、环境变量配置（云函数 bijingSync）

所有对接必经后台的地址与 Token 均通过云函数环境变量注入，**代码内不写任何默认值、前端不持有任何密钥**。改环境（测试 ↔ 生产）只需在控制台改环境变量，**无需改代码、无需发版、前端无感**。

### 1. 配置入口（微信云开发控制台）
1. 打开「云开发」控制台 → 左侧「云函数」→ 找到 `bijingSync`。
2. 进入 `bijingSync` → 「配置」Tab → 找到「环境变量」区域（或小齿轮图标）。
3. 点击「编辑」，新增/修改下列环境变量并保存。更新代码仍需单独上传并部署云函数；部署后再次核对目标环境中的配置。仅修改环境变量时按控制台的保存／发布提示使配置生效，无需为了环境变量修改重复上传触发器。

### 2. 对端变量与取值
| 变量名 | 说明 | 测试环境值 | 生产环境值 |
|--------|------|-----------|-----------|
| `BIJING_API_BASE` | 对端 API 基地址（决定走测试库还是生产库） | `https://data.bjzl.net.cn` | `https://data.bijing.life` |
| `BIJING_ACCESS_TOKEN` | 接口鉴权令牌（`X-Access-Token` 请求头） | `JINGZUO_XIAOCHENGXU` | `JINGZUO_XIAOCHENGXU` |

> 两个环境的 Access Token 当前一致；如后续对端区分测试/生产令牌，按对端实际下发值填写即可。

启用原生微信定时同步还须在同一个 `bijingSync` 云函数配置 **`BIJING_TIMER_ENABLED=true`** 和 **`BIJING_TIMER_SOURCE=wx_trigger`**（均为不带引号的文本）。来源取平台 `cloud.getWXContext()`，不能通过请求参数自行指定。单独的「标准触发器」是否满足来源要求须实测，不应修改鉴权值来迁就未知来源。详细身份边界见 [运维入口说明](../docs/maintenance-access.md)。

### 3. 测试环境 ↔ 生产环境切换
- **从测试切生产**：将 `BIJING_API_BASE` 由 `https://data.bjzl.net.cn` 改为 `https://data.bijing.life`，按控制台提示保存／发布配置并验证实际访问主机。
- **从生产切回测试**：反向改回 `https://data.bjzl.net.cn`，保存／发布配置并验证。不同环境应各自部署；不要通过反复切换同一环境的 API 地址来代替隔离测试。
- 切换后**已绑定的用户无需重新绑定**，后续同步会自动指向新地址；历史的 `bijingSyncedDates` 状态保留用于展示，不会阻止向新环境上报。

### 4. 未配置 / 配置错误的表现
- 若漏配 `BIJING_API_BASE` 或 `BIJING_ACCESS_TOKEN`，云函数会在实际调用时**主动抛错**（不再有兜底默认值），调用日志会出现：
  - `缺少环境变量 BIJING_API_BASE，请在云函数配置中设置`
  - `缺少环境变量 BIJING_ACCESS_TOKEN，请在云函数配置中设置`
- 此时绑定/同步均会失败，需在控制台补填并使配置生效；已遗漏的业务日期需按失败日志手动补报。

### 5. 配置生效验证
配置生效后，可用以下任一方式确认环境正确：
- 在 me 页绑定一个**已存在学号**（如 `BJ2407159`），观察云函数日志里 `🔍 校验学号存在性` 打印的 URL 主机名：
  - 测试环境应为 `data.bjzl.net.cn`；
  - 生产环境应为 `data.bijing.life`。
- 或直接 curl 对端校验（替换 `BIJING_API_BASE` 与学号）：
  ```bash
  curl -H "X-Access-Token: JINGZUO_XIAOCHENGXU" \
    https://data.bjzl.net.cn/api/openapi/users/BJ2407159
  ```
  能返回 `success:true` 与昵称即说明该环境地址/令牌可用。

## 四、部署步骤

1. 上传 `bijingSync` 云函数（右键 → 上传并部署：云端安装依赖）。
2. 在云函数配置中保留对端地址、令牌，并配置 `BIJING_TIMER_ENABLED=true`、`BIJING_TIMER_SOURCE=wx_trigger`。执行超时不要继续使用 3 秒，可从 **60 秒** 做小规模测试，再根据用户数和实际耗时调大。首次测试环境接入时可先关闭定时开关，按 [运维入口说明](../docs/maintenance-access.md) 验证真实来源后启用。
3. 确认 `bijingSync/config.json` 的 `dailySyncBijing` timer 表达式为 **`0 0 2 * * * *`（每天北京时间 02:00）**。只有云端规则需要更新时才单独「上传触发器」，只保留一条每日任务，避免与旧 04:00 规则并存。如果此前部署过批量版本，还须在云端删除 `resumeBijingBatches` 每分钟触发器；恢复单学号版本后不再需要续跑触发器。
4. 编译小程序，进入「我」页，应看到「必经之路同步」区块。
5. 发布新版前先部署 `meditationManager` 和 `bijingSync`：前者负责按 `timestamp` 归属计时日期、按显式 `date` 保留手动补录日期，后者负责按 02:00 切日预览和上报，再更新小程序。仅编译小程序或只部署 `bijingSync` 都不会更新打卡写入逻辑。
6. 运行 `npm run test:bijing-sync`，其中链路测试覆盖前端传入时间 → `meditationManager` 入库 → `bijingSync` 预览。部署后下载云端 `meditationManager/index.js` 与待发布文件比对，不能仅凭“已部署”状态判断是否为最新版。

## 五、闭环验证清单（测试环境）

1. **绑定学号 + 昵称覆盖**
   - 在「我」页点「绑定学号」，输入已存在学号（如 `BJ2407159`）。
   - 预期：提示「已绑定并同步昵称」，`me` 页昵称立即变为对方昵称；`users` 文档 `bijingBound=true`、`bijingStudentNumber` 写入、`nickName` 被覆盖。
   - 若输入不存在学号：提示「学号不存在」，绑定失败。

2. **制造昨天打卡数据**
   - 在测试账号下，确保 `meditation_records` 存在时间戳在昨天 02:00 至今天 02:00 前的记录（duration 任意，如 30）。
   - 额外覆盖昨天 01:59:59、昨天 02:00、今天 01:59:59、今天 02:00，只有中间两条应计入昨天。

3. **手动同步**
   - 02:00 后点「手动同步」，弹窗提供昨天至 7 天前，默认昨天；02:00 前提供前天至 8 天前。日期列表可上下滚动，应能选择全部 7 个日期；取消不会发起同步。
   - 选定日期后自动读取明细，显示每条打卡的时间、时长，以及「共 N 次，合计 M 分钟」；超过列表高度可滚动查看。
   - 快速切换日期，旧请求不得覆盖新日期；读取失败时展示重试入口，不得把失败显示为 0 次或允许同步。
   - 选定日期后点「同步这一天」；请求参数 `recordDate` 应为所选日期，其他日期不应上报。
   - 首次及重复同步成功都显示「YYYY-MM-DD 已同步 N 分钟」；无记录显示「YYYY-MM-DD 暂无打卡记录」。
   - 无记录或失败不写新的成功状态，失败后可以重试；成功日期再次同步应重新请求对端。补录后再次同步应上传最新合计，相同学号和日期由对端幂等覆盖。
   - 分别验证自动后手动、手动后自动，以及重复触发自动同步，同一天每次均重新上报，故障后的重试也不应产生累加数据。
   - 第 7 个已结束同步日应可预览并同步；直接调用云函数提交今天、未来、尚未结束或超出七个已结束同步日的日期，应被拒绝。
   - 弹窗打开后跨过北京时间 02:00，已过期的日期不能提交，需要重新选择；跨自然日零点不会改变同步窗口。

4. **对端验证**
   - 用 curl 调对端查询/确认：
     ```bash
     curl -H "X-Access-Token: JINGZUO_XIAOCHENGXU" \
       https://data.bjzl.net.cn/api/openapi/meditation/heatmap?studentNumber=BJ2407159
     ```
   - 预期：`data.records` 中存在 `date=昨天`、`duration=30` 的记录（当天合计分钟数）。`/api/openapi/meditation/records` 仅提供 `POST` 写入，不提供 `GET` 查询。

5. **定时任务与失败重试**
   - 使用实际原生微信触发器；普通客户端或控制台测试请求不能通过填写 `source` 冒充定时器。人工调用 `{ "type": "cronSyncAll" }` 仅限服务端管理员白名单中的已认证身份。
   - 预期：逐个处理全部 `bijingBound=true` 用户，各自同步最近已结束日；02:00 前手动调用不会上报仍未结束的昨天。返回 `data.date`、`data.total`、`data.success`、`data.failed` 及失败明细 `data.failedUsers`，核对对端最终合计。
   - 在测试环境模拟一次临时失败后成功，确认重试后继续下一位；模拟持续失败，确认首次尝试加 3 次重试后记录失败并继续下一位。成功或无可同步时长的跳过结果不应触发失败重试。
   - 任何最终失败均应使顶层 `success:false`，并可从日志或 `data.failedUsers` 定位同学、业务日期和错误。失败日期处于个人手动同步允许范围内时可补报，超出范围的日期需另行处理。
   - 用实际规模测量全轮耗时并设置平台执行超时。代码未增加持久化队列或断点续跑；本地隔离测试不能替代真实 SDK、定时来源、执行超时与对端幂等行为的部署验证。

6. **时区一致性核对**
   - 在云函数内打印 `getBusinessDate(new Date())` 与小程序 `dateUtil.getBusinessDate()`，应完全一致（东八区）。
   - 确认云端和前端同步日期均在北京时间 02:00 切换；自动记录的 `meditation_records.date` 与对端 `recordDate` 均采用该业务日；00:00–01:59 归前一天，02:00 起归当天。

## 六、已知问题修复：8.1 漏同步（标记语义修正）

### 现象
绑定学号并多次打卡后点「立即同步」，结果「成功 1 天、跳过 1 天」，但 **2026-08-01 的 30 分钟数据始终未同步到对端**。

### 根因
打卡是本地优先 + 异步备份到云端（`checkin.js#asyncBackupToCloud`）。某次 `syncDate` 扫描 8.1 时，云端 `meditation_records` 中该 openid 当天记录**尚在异步备份途中、查不到**，`getDayDuration` 返回 0。旧逻辑在 `duration<=0` 分支调用了 `markSynced`，把 8.1 永久标为 `bijingSyncedDates["2026-08-01"]=true`。

之后 8.1 的 2 条记录（各 15 分钟）虽成功到达云端，但 `syncDate` 开头的去重判断 `if (synced[dateStr]) return skipped` 直接命中已标 `true`，**再也不会重新核算上报**，形成"已标 true 却未真正同步"的死锁。

### 当时的修复（仅改 `bijingSync/index.js`，当前窗口与重复同步规则见上文）
- `syncDate` 的 `duration<=0` 分支**移除 `markSynced` 调用**：查不到数据不再写标记，留待后续同步复查。
- 标记语义收紧为：**只有对端真实返回成功才标 `true`**；"无打卡数据/查不到"与"已同步成功"不再共用同一永久标记。
- 同步窗口由「绑定日 → 昨天」扩展为「绑定日 → 今天」（含当天，便于当天补报）。

### 验证结果
- 已在云数据库手动删除 `bijingSyncedDates["2026-08-01"]` 旧键，重新点「立即同步」：8.1 的 30 分钟成功上报对端，`bijingSyncedDates["2026-08-01"]` 正确标 `true`。
- 其余历史日期同步正常，无重复写入。

### 遗留与约束
- 已存在的旧误标 `true` 不会自动清除，但已不再阻止上报；范围内的日期可直接再次同步，无需手动删键。
- 手动同步默认允许重复上报；旧调用中的 `force:true` 不会清除同步状态或扩大最近七个已结束同步日的范围。更早日期需单独处理。

## 七、注意事项

- 定时来源以平台上下文精确鉴权；无 OPENID 本身不是授权。云函数按分页读取绑定用户，再逐个串行同步；分页仍在同一次执行里，不会重置平台超时。
- 失败处理：首次失败后额外重试最多 3 次，仍失败则记录 `failedUsers` 并继续下一位；只有对端成功才写成功状态，有最终失败时明确返回部分失败。没有跨调用进度恢复，平台超时或最终失败应根据日志手动补报。
- 自动与手动同步依赖外部接口的同号同日覆盖契约；用户量大时需根据实际整轮耗时配置执行超时，增加重试次数本身不能保证整轮一定跑完。
- 补录依赖 `meditationManager` 保留传入的业务日期及时间；同步查询仍以云端原始记录为准。
