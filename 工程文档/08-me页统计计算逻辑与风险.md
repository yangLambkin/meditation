# 08 - me 页统计计算逻辑与风险

> 逆向自 `miniprogram/pages/me/me.js`、`miniprogram/utils/checkin.js`、`cloudfunctions/meditationManager/index.js`。
> 聚焦「我」页面的四项统计（`totalMinutes` / `consecutiveDays` / `currentStreak` / `medals`）的数据来源、计算链路与已知错误/风险。

---

## 1. 数据来源总览

`me` 页面四项统计的**数据来源并不统一**——三项来自云端聚合 `user_stats`，一项来自本地缓存：

| 展示字段 (data) | wxml 文案 | 取值表达式 | 数据来源 | 来源类型 |
|---|---|---|---|---|
| `totalMinutes` | 当月总分钟 | `stats.monthlyStats[当前月].totalDuration`（离线回退 `getCurrentMonthMinutes`） | 云端 `user_stats` 按月聚合（在线）/ 本地 `dailyRecords`（离线） | **云端为主** |
| `consecutiveDays` | 最长连续天数 | `stats.longestCheckInDays \|\| 0` | 云端 `user_stats` | 云端聚合 |
| `currentStreak` | 坚持静坐第 X 天 | `stats.currentStreak \|\| 0` | 云端 `user_stats` | 云端聚合 |
| `medals` | 勋章 | `badgeManager.getUnlockedCount()` | 本地（已与云端同步） | 本地缓存 |

⚠️ 关键点：**同一页面的四项统计，三项走云端，一项走本地**。这是后续多数风险的根因。

---

## 2. 计算流程

```
onLoad / onShow
  └─ getUserData()
       ├─ getUserNickname()         // 缓存 userNickname
       ├─ getUserAvatar()           // 缓存 userInfo.avatarUrl
       └─ calculateUserStatistics() // async
            ├─ 重新推导登录态（userOpenId 是否 'oz' 开头 / 是否有 userInfo / nickname）
            ├─ isLoggedIn → getUserStatisticsFromCloud(userOpenId)
            │     ├─ cloud.callFunction('meditationManager', {type:'getUserStats', openid})
            │     ├─ badgeManager.loadBadgesFromCloud()
            │     ├─ badgeManager.checkBadgeUnlock({currentStreak, totalCheckinDays, lastDuration, totalDuration})
            │     ├─ badgeManager.getUnlockedCount()  → medals
            │     ├─ stats.monthlyStats[当前月].totalDuration  → totalMinutes   ← 云端（失败回退本地 getCurrentMonthMinutes）
            │     └─ setData({ totalMinutes, consecutiveDays: stats.longestCheckInDays,
            │                   currentStreak: stats.currentStreak, medals })
            └─ else → 全部置 0
```

- 登录态判定在 `me.js` 内**重复实现**（未复用 `checkin.isUserLoggedIn`），与 `index` 页面逻辑各自为政，存在漂移风险。
- `onLoad` 与 `onShow` 都会触发 `calculateUserStatistics`（两个生命周期），且该方法是 `async`，**可能并发两次云端调用**（无去重/锁）。
- 获取失败时（云端成功=false 或异常）`totalMinutes/consecutiveDays/currentStreak` 置 0，但 `medals` 回退为本地已解锁数——失败场景下四项口径再次不一致。

## 3. 各项计算细节

### 3.1 `totalMinutes`（当月总分钟）—— 云端为主（4.1 已修复，2026-07-28）
链路：`me.js#152-159` 优先取 `stats.monthlyStats[当前月].totalDuration`（`getUserStats` 返回的 `user_stats` 按月聚合值），与 `currentStreak`/最长连续天数同源；仅在云端获取失败/异常时回退到本地 `checkinManager.getCurrentMonthMinutes()`（`checkin.js#1178`，读 `dailyRecords` 按月过滤求和，带 1 小时缓存）。

> 修复前该字段完全走本地，存在换设备/清缓存后偏 0 的风险；修复后与另外三项同为云端口径。

### 3.2 `consecutiveDays`（最长连续天数）—— 云端字段
`me.js#157` 直接取 `stats.longestCheckInDays`。该字段由 `recordMeditation`（`meditationManager/index.js#196-201`）维护。

### 3.3 `currentStreak`（当前连续天数）—— 云端字段
`me.js#158` 直接取 `stats.currentStreak`，由 `recordMeditation#203-220` 维护（仅在 `isNewDay` 时按日期差 `diffDays` 递增/重置）。

### 3.4 `medals`（勋章数）—— 本地、已与云端同步
`me.js#138-149`：先 `loadBadgesFromCloud()` 拉云端勋章，再 `checkBadgeUnlock(...)` 用本次 stats 评估新解锁，最后 `getUnlockedCount()`。

## 4. 错误与风险分析

### 4.1 [中-高] `totalMinutes` 走本地，与其余三项云端口径不一致（数据可靠性风险）
- 已登录用户的 canonical 数据在云端，但「当月总分钟」却读本地 `dailyRecords`。
- 当用户**换设备 / 重装 / 本地缓存被清 / 缓存恢复不完整**时，本地 `dailyRecords` 可能缺失记录 → `totalMinutes` 显示 0 或偏小；而 `currentStreak`/`最长连续天数` 来自云端仍正确。结果是**同一页面两项统计自相矛盾**。
- 佐证：`me.js#284-316` 里存在一个**从未被调用的云端版本** `calculateCurrentMonthMinutes`（调用 `meditationManager.getMonthlyStats`），说明原本打算用云端，后改本地却留下死代码。

**建议**：改为优先使用云端按当月聚合的值 `stats.monthlyStats[当前YYYY-MM].totalDuration`（`getUserStats` 已返回该嵌套对象，见 `meditationManager/index.js#426`），本地仅作离线回退。删除死代码 `me.js#284-316`。

**✅ 已修复（2026-07-28）**：`me.js` 成功分支改为读取 `stats.monthlyStats[当前月].totalDuration`；失败分支保留本地 `getCurrentMonthMinutes()` 作离线回退；并删除了 `me.js` 中从未调用的死代码 `calculateCurrentMonthMinutes`。现 `totalMinutes` 与 `currentStreak`/最长连续天数同为云端口径，换设备/清缓存不再偏 0。

### 4.2 [中] 云端 `monthlyTotalDuration` 从不按月重置（相关云函数 bug，污染"当月"语义）
- `recordMeditation`（`meditationManager/index.js#190-193`）中 `monthlyTotalDuration` **始终 `db.command.inc(duration)`**，跨月不清零 → 实际是"累计总时长"而非"当月"。
- `me` 页因改用本地按月过滤而**侥幸避开了**这个字段，但若任何排行/快照/其他页面误用 `monthlyTotalDuration` 当"当月值"都会出错。
- 真正正确的云端当月值在 `monthlyStats[YYYY-MM].totalDuration`（#224-236 已按当月正确累加）。

**建议**：要么在跨月首次打卡时重置 `monthlyTotalDuration`，要么明确其"累计"语义并改名（如 `lifetimeTotalDuration`），避免误用。

**✅ 已修复（2026-07-28）**：`recordMeditation`（`meditationManager/index.js#190-193`）现先比较 `stats.lastCheckinDate` 的月份 `lastMonthStr` 与本次 `monthStr`，若跨月（`lastMonthStr !== monthStr`）则把 `monthlyTotalDuration` 重置为当月本次 `duration`，否则保持 `inc`。自此 `monthlyTotalDuration` 真正表示"当月"，与 `monthlyStats[当月].totalDuration` 语义一致。

### 4.3 [低-中] `longestCheckInDays` 在同一天多次打卡时被高估（直接影响"最长连续天数"展示）
- `recordMeditation#196-201`：`longestCheckInDays` 更新使用 `stats.currentStreak + 1`，且**不受 `isNewDay` 限制**（无条件执行）；而 `currentStreak` 仅在 `isNewDay` 时才递增（#203-220）。
- 后果：同一天第 2 次打卡会把 `longestCheckInDays` 抬到 `currentStreak + 1`，导致"最长连续天数"**虚高**。
  - 例：第 1 天打卡 3 次 → `currentStreak=1`，但 `longestCheckInDays` 会被抬到 2；用户实际只连续 1 天。
- `me` 页 `consecutiveDays` 直接展示该字段（#157），故会显示错误值。

**建议**：`longestCheckInDays` 的更新应只在真正发生"连续天数增长"时（即 `isNewDay && diffDays===1`）按 `currentStreak` 取 `max`，或在统计端改用独立的"最长连续天数"重算，而非借用 `currentStreak+1` 的近似。

**✅ 已修复（2026-07-28）**：`recordMeditation`（`meditationManager/index.js#203` 段）现先按 `isNewDay && diffDays` 推算本次打卡后的真实连续天数 `newStreak`，再用 `max` 更新 `longestCheckInDays`。同天多次打卡时 `newStreak` 保持 `stats.currentStreak` 不变 → 不再虚高；跨天连续时正常取 `currentStreak+1`。

### 4.4 [低] `consecutiveDays` 变量命名误导
- 变量名 `consecutiveDays`（"连续天数"）实际取 `longestCheckInDays`（"最长"）；wxml 文案"最长连续天数"正确，但代码变量名易被后续维护者误用为"当前连续"。
- **建议**：改名为 `longestCheckInDays` 或 `longestStreakDays` 以与语义一致（注：云端另存在 `longestStreak` 字段，`longestCheckInDays` 与 `longestStreak` 语义需二选一统一）。

**✅ 已修复（2026-07-28）**：`me.js` 的 `data`、成功/失败分支 `setData` 及 `me.wxml` 展示变量均由 `consecutiveDays` 统一改为 `longestCheckInDays`，与云端 `user_stats.longestCheckInDays` 字段名一致，消除命名误导。

### 4.5 [低] 登录态判定重复实现
- `me.js#85-102` 自行拼装 `isWechatLoggedIn/hasWechatInfo/isLoggedIn`，与 `index` 页面、`checkin.isUserLoggedIn`（`checkin.js#1293`）各写一套，未来登录逻辑变更易漏改。
- **建议**：统一调用 `checkin.isUserLoggedIn()` / 一个共享的 `authManager`。

**✅ 已修复（2026-07-28）**：`me.js#calculateUserStatistics` 删除重复的本地判定，改为直接复用 `checkinManager.isUserLoggedIn()`；仅其返回 true 时才用 `userOpenId` 调云端。本地未登录但设过昵称的用户不再被误判为已登录、不再用非 openid 调云端。

### 4.6 [低] `onLoad`+`onShow` 双触发无去重
- 两者都调 async `calculateUserStatistics`，进入页面时可能并发两次 `getUserStats` 云端调用。
- **建议**：加一个 `this._loadingStats` 标志位去重，或仅在 `onShow` 调用。

**✅ 已修复（2026-07-28）**：`me.js` 在 `data` 同级新增实例属性 `_loadingStats: false`；`calculateUserStatistics` 入口 `if (this._loadingStats) return;` 加锁，`finally` 中释放。进入页面时 `onLoad`+`onShow` 并发只触发一次云端调用。

### 4.7 [低-中] badge 页 `totalCheckinDays` 字段名错配（潜伏 bug，已修复）
- `badge.js#79` 与 `me.js#147` 取云端 `stats.totalCheckinDays`，但云端 `getUserStats`（`meditationManager/index.js#412-427`）返回的是 **`totalDays`**（累计打卡天数），**没有 `totalCheckinDays`** 字段 → 该值恒为 `undefined` → 兜底成 **0**。
- 影响：`badgeManager.checkBadgeUnlock` 的 `total_checkin` 解锁分支依赖 `totalCheckinDays`，一旦新增「累计打卡天数」类勋章将**永远无法解锁**；当前配置无此类勋章故无可见症状，但是个陷阱。
- **已修复**：两处统一改为 `stats.totalDays`（语义匹配"累计打卡天数"）。

### 4.8 [低] badge 页 `onLoad`+`onShow` 双触发无去重（与 4.6 同类，已修复）
- `badge.js` 的 `onLoad` 与 `onShow` 都调 async `loadBadgeData`，进入页面会并发两次云端调用（`loadBadgesFromCloud` + `getUserStats` + 可能 `checkBadgeUnlock`）。
- **已修复**：在 `loadBadgeData` 入口加 `this._loadingBadge` 标志位去重，请求完成（含 catch）后在 `finally` 释放。

### 4.9 [低] badge 页 wxml 内层 `wx:for` 变量名遮蔽外层（已修复）
- `badge.wxml` 内层 `wx:for="{{item.badges}}"` 仍用默认变量名 `item`，会遮蔽外层分类循环的 `item`，可读性差（功能无误，因 `wx:key="id"` 仍有效）。
- **已修复**：内层显式 `wx:for-item="badge"`，并把 `{{item.imageUrl}}`/`{{item.name}}` 改为 `{{badge.imageUrl}}`/`{{badge.name}}`。

## 6. 全局根因补充修复（2026-07-28）

### ③ UTC 日期基准（全局根因，✅ 已修复）
- **问题**：业务"今天/本月"此前用 `new Date().toISOString().split('T')[0]` 生成日期字符串。`toISOString()` 返回 **UTC** 时间，导致中国时区（UTC+8）在每日 00:00–08:00 期间，生成的日期比本地实际日期**小一天/一个月**，进而：
  - 打卡记录 `date` 字段记成前一天 → 与前端"今日已打卡"判断错位；
  - 跨月/跨天连续天数（streak）判定偏差；
  - 当月聚合 `monthStr`、排名快照周期、团队周范围等全部错位；
  - 云端（云函数容器时区）与前端（手机本地时区）若各自用 `toISOString`/`getDate`，还会因运行环境时区不同而**相互矛盾**。
- **修复方案**：新建统一工具 `miniprogram/utils/dateUtil.js`，提供 `getBusinessDate()` / `getBusinessMonth()`，显式按**东八区（中国时区 UTC+8）**计算业务日期（"时间 +8h 后取 UTC 分量"技巧，规避运行环境本地时区差异），保证前后端使用完全一致的唯一日期基准。云函数（`meditationManager`、`cleanupTestData`）与本地脚本（`runCleanup.js`）内联同款函数。
- **影响文件**：
  - 前端：`utils/checkin.js`、`pages/me/me.js`、`pages/recorder/recorder.js`、`pages/history/history.js`、`pages/daily/daily1.js`、`subpackages/team/pages/teamDetails/teamDetails.js`
  - 云函数：`cloudfunctions/meditationManager/index.js`、`cloudfunctions/cleanupTestData/index.js`
  - 脚本：`scripts/runCleanup.js`
- **验证**：Node 单测覆盖东八区边界（BJ 00:30 / 07:59 / 08:00 / 跨月 02-01 0:00 / 跨月 08-01 0:00）均归属正确，无回归。
- **未改动**：纯时间戳类 `toISOString()`（如 `loginTime`/`createdAt`/`updatedAt`/`lastUpdateTime`/`unlockTime`）仅作绝对时间点记录，不受日期基准影响，保持原样。

### ② 1 小时缓存陈旧（仍遗留，未处理）
- `checkin.calculateCurrentMonthMinutes` 的月度缓存有效期为 1 小时（`isMonthlyCacheValid`），用户当日内多次打卡后最长需等 1 小时才刷新本地月统计。属体验问题，非数据错误，留待独立优化。

## 7. 勋章获取逻辑（专项）

> 逆向自 `miniprogram/utils/badgeManager.js`、`pages/me/me.js`、`pages/badge/badge.js`。
> 勋章是 `me` 页四项统计之一的 `medals`（`badgeManager.getUnlockedCount()`），本节说明其完整"配置 → 解锁判定 → 触发 → 本地缓存 → 云端同步"链路。

### 7.1 勋章配置总览
配置集中在 `badgeManager.js` 的 `badgeConfig`，每条含 `condition`（类型 + 阈值）与展示信息。共 3 类 17 枚：

| id | 名称 | 分类 | 条件类型 `condition.type` | 阈值 | 判定依据字段 |
|---|---|---|---|---|---|
| `continuous-7/14/30/60/100/365` | 连续打卡 7/14/30/60/100/365 天 | continuous | `continuous_checkin` | days=7/14/30/60/100/365 | `currentStreak`（连续打卡天数） |
| `meditation-20` | 单次觉察 20 分钟 | duration | `single_duration` | minutes=20 | `lastDuration`（最后一次打卡时长，分钟） |
| `level-1` ~ `level-10` | LV1.新手 ~ 禅定大师 | level | `total_duration` | minutes=10/100/300/600/1000/2000/4000/8000/15000/30000 | `totalDuration`（累计打卡时长，分钟） |

> ⚠️ `checkBadgeUnlock` 还支持 `total_checkin` 类型（按 `totalCheckinDays` 累计天数判定），**但当前 `badgeConfig` 没有任何勋章使用该类型**，属死代码分支（详见 7.5 风险2）。

### 7.2 解锁判定（checkBadgeUnlock）
入口入参结构（由调用方从 `user_stats` 映射而来）：
```js
{ currentStreak, totalCheckinDays, lastDuration, totalDuration }
```
遍历 `badgeConfig` 全部勋章，已解锁（`isUnlocked`）直接跳过；按 `condition.type` 分支比较：
- `continuous_checkin`：`currentStreak >= condition.days`
- `total_checkin`：`totalCheckinDays >= condition.days`（当前无配置）
- `single_duration`：`lastDuration >= condition.minutes`
- `total_duration`：`totalDuration >= condition.minutes`

任一勋章满足条件即 `unlockBadge` 并记 `hasNewUnlock=true`。循环结束若 `hasNewUnlock`，则 `saveBadgesToStorage()` + `syncBadgesToCloud()`。
`unlockBadge` 内部：置 `isUnlocked=true`、`unlockTime = new Date().toISOString()`，并**立即**再尝试一次 `syncBadgesToCloud`（失败仅告警，不阻断本地解锁）。

### 7.3 触发时机
- **me 页**：`calculateUserStatistics` 在 `getUserStats` 成功后调用（见 `me.js#138-143`），入参映射为 `currentStreak: stats.currentStreak`、`totalCheckinDays: stats.totalDays`、`lastDuration: stats.lastCheckinDuration`、`totalDuration: stats.totalDuration`。随后 `getUnlockedCount()` 驱动 `medals` 展示。
- **badge 页**：`loadBadgeData` → `getUserStatistics()`（`badge.js#68-97`，同样映射）→ `checkBadgeUnlock`（见 4.8/4.9 节）。
- **打卡流程（recorder/timer，✅ 已覆盖）**：`recorder` 的 `recordCheckin`（`checkin.js#682`）内部调用 `asyncCheckBadgeUnlock(duration)` → `badgeManager.checkBadgeUnlock`；`timer` 页以 `duration` 跳转 `recorder`，复用同一路径。因此用户**完成一次满足解锁条件的打卡后即会即时解锁**（见 7.5 风险1，已修复）。
- **登录后（profile，✅ 已覆盖）**：`profile` 微信登录成功后调 `checkBadgeAfterLogin()` → `checkBadgeUnlock`，作为登录态补评（见 4.x）。

### 7.4 本地缓存与云端同步
- **本地缓存**：键名 `getBadgeStorageKey()` = `userBadges_${userOpenId}`，按用户隔离。注意：未登录时 `userOpenId` 实为自生成的 `local_xxx`（**非空**），故 key 实际是 `userBadges_local_xxx` 而非 `userBadges_guest`（`_guest` 分支仅在 `userOpenId` 彻底为空时触发，实践中几乎不出现）。仅持久化 `{ isUnlocked, unlockTime }`（合并自 `badgeConfig` 默认配置）。登录换绑时由 `migrateBadges` 将 `userBadges_local_xxx` → `userBadges_oz...`（详见 7.5 风险3）。
- **上传云端**：`syncBadgesToCloud()`（`wx.cloud.callFunction` → `meditationManager.updateUserBadges`），只同步**已解锁**勋章的 `name`/`unlockTime`，缺 openid 时跳过。
- **拉取云端**：`loadBadgesFromCloud()`（`getUserBadges`）做**云端→本地单向增量合并**——仅把云端已解锁且本地尚未解锁的勋章标记为已解锁并落盘；本地→云端不在此处回写（回写在解锁时由 `syncBadgesToCloud` 完成）。

### 7.5 已知风险与注意（2026-07-28 复核）

> 以下 4 项原风险，本次已逐项处理：①/③ 已修复（代码 + 文档），② 已加固，④ 为说明性事项无需改代码。

1. **解锁时机延迟（✅ 已修复）**：经复核，打卡流程实际已通过 `checkin.recordCheckin` → `asyncCheckBadgeUnlock(duration)` 即时调用 `checkBadgeUnlock`（`recorder` 走此路径，`timer` 经 `recorder` 复用）；`profile` 登录后还有 `checkBadgeAfterLogin` 补评。因此新勋章在打卡完成页即会即时解锁与云端同步，不再依赖进入 `me`/`badge` 页。原"关键缺口"描述已更正（见 7.3）。
2. **`total_checkin` 分支为死代码（✅ 已加固）**：当前 `badgeConfig` 无勋章使用该类型；已在该分支加注释，明确调用方**必须传入 `totalCheckinDays: stats.totalDays`**（历史曾因字段名错配导致恒为 0），避免未来新增"累计天数"类勋章时重踩。该分支当前无害、保留备用。
3. **未登录（local_）勋章不继承（✅ 已修复）**：
   - **真实场景修正**：未登录时 `userOpenId` 实为自生成的 `local_xxx`（非空），故本地勋章存于 `userBadges_local_xxx`，而非 `userBadges_guest`；登录后 `userOpenId` 切为微信 `oz...`，key 变为 `userBadges_oz...`，旧 `userBadges_local_xxx` 不被继承。
   - **隐患**：`checkBadgeAfterLogin` 复评时 `lastDuration` 为 0，导致 `single_duration` 类（`meditation-20`）等本地已解锁但登录时无法重新满足条件的勋章**丢失**。
   - **修复**：新增 `badgeManager.migrateBadges(fromOpenid, toOpenid)`，在 4 个登录换绑点（`index.js#saveBasicUserInfo`/`saveUserInfo`、`profile.js#微信登录成功`/`saveToLocalStorage`）调用，将旧 key 中已解锁勋章（含 `unlockTime`）合并到新 openid 缓存，并触发一次云端同步。迁移对 `from===to` 或旧 key 为空时为 no-op，安全幂等。
4. **`unlockTime` 时间戳不受根因③影响（说明性，无需改）**：`unlockBadge` 用 `new Date().toISOString()` 记录的是**瞬时时间戳**（解锁时间展示/排序），并非"日期归属字符串"，不受第 6 节③的 UTC 日期偏移影响，保持原样。

> 关联：badge 页的 4.7（字段错配）、4.8（双触发去重）、4.9（wxml 变量遮蔽）均属勋章展示链路，已修复；本节补充其上游"获取/解锁"逻辑。
