第三批技术方案：历史迁移、增量同步、汇总与性能治理

状态：待实施。依赖 [第一批](2026-09-22-plan-01-correctness-and-access.md) 的修复与 [第二批](2026-09-22-plan-02-state-and-domain.md) 的单写入口、共享规则和同步任务。目标是在持续产生新记录时安全迁移历史，并让常用请求的成本主要随本次变化量增长。

**兼容底线。** 旧 `getAllRecords` 必须继续返回完整、一致的数组快照。现有客户端会把完整成功快照中缺失的已同步记录解释为云端删除；绝不能把这个接口原地改成一页或一批增量。新增 V2 协议，按客户端能力选择；V1 保留到旧版本使用量达到明确下线条件。网络失败、响应截断或分页未完成不得被标记为完整快照。

**步骤 1：先量化成本，制定准入目标。** 在测试环境构造每用户 100、1000、10000 条记录的样本，覆盖 1/10/50 人团队、不同体验文本长度、旧格式和上传队列；实际单文档、事务和响应限制以当前云环境为准。收集本机读取/写入字节、setData 字节、页面处理耗时、云端数据库调用次数与扫描量、接口 p50/p95、超时率和每轮任务处理量。

硬性验收包括零记录丢失、零未确认记录误删、零身份误合并。性能目标先采用可确定的结构标准：普通新记录写入不扫描完整历史；查一天不读取其他日期；增量无变化时不传全部历史；首页渲染量随可见记录而非终身历史增长。具体毫秒和并发值在基线测量后写入验收记录，不能把预估当成已达到的 SLA。

**步骤 2：先补齐所有写入的变更日志，再做迁移。** 在现有用户 `meditation_locks.revision` 机制上新增受保护变更日志，记录、统计所需更新、revision 和变更事件在同一事务提交。覆盖创建、删除、体验修改、重复合并、日期迁移、后台修复等全部相关入口；绕过服务直接写库的权限必须收口。旧客户端调用的旧接口也由新服务端写日志。

建议每次提交生成一个唯一事件 `{owner, epoch, seq, operations, committedAt}`，`seq` 使用该用户事务 revision，operations 包含 upsert 完整后像或 delete 标识。提交失败无事件；幂等重放原记录不制造新业务变化。一个提交含多操作时事件大小必须受控，超限任务拆成可验证的小批次，而不是写无限数组。

勋章等不改变记录视图的事务可以推进 revision 而无记录事件，因此 seq 不要求连续整数；完整性由受控写入协议、日志起点、保留水位与 epoch 保证，不能把任意序号空隙当数据丢失。变更事件保存对应版本内容，不能消费时再读取可能已经更新或删除的当前文档代替事件内容。

记录删除时另存稳定身份的删除凭证，与原记录删除、变更事件在同一事务提交。迟到上传或另一台设备重放相同 clientRecordId 时返回明确的 `RECORD_DELETED`，不能重新创建已删除记录，也不能返回一个实际不存在的成功 recordId。重新记录一次真实静坐使用新的会话身份。变更日志的保留期与删除身份凭证的保留期分别设计：清理旧日志不能同时遗忘删除身份，否则长期离线设备可能复活已删记录。旧无稳定身份记录仍走原有人工确认/歧义检查，不凭时间戳猜测属于哪个删除凭证。

**步骤 3：构建可续跑的历史迁移任务。** 先扫描生成报告，包含字段类型、缺失身份、手动日期、稳定身份重复、冲突正文、无可靠时间戳、每用户记录量，以及预计事务规模。先保存可恢复导出与迁移元数据，再以受保护任务执行；不调用现有 `cleanupTestData` 代替迁移。

采用显式目标清单及 checkpoint，优先按用户处理。用户清单须覆盖 users、user_stats 与记录归属的并集，并用幂等去重；不能只按当前活跃用户查询，以免遗漏无资料的旧用户。游标只用于遍历，新增哈希 ID 可能落在游标前，必须通过写入协议和最终校准保证覆盖，不能声称 `_id` 游标天然代表完整快照。

记录迁移规则：自动记录按原始可靠时间归属北京时间 `[02:00, 次日02:00)`；显式手动记录保留选定业务日期；无可靠时间保留原合法日期并标记来源；无合法日期的进入隔离报告，不猜测、不丢弃。时间戳规范化保留原值备查。只按同用户稳定身份合并，合法的同时间同分钟记录保留。旧体验、别名与映射必须保留，不能丢正文或让仍持旧 ID 的客户端失去定位能力。

本批增加/确认查询字段 `businessDate`、数值时间字段及模型版本，通过兼容 serializer 继续输出旧 `date/timestamp`。不要同时维护两个可独立写的日期：由同一领域函数生成并在同一次写入更新。确定具体字段名后，把映射写入 schema 清单。

现有 `migrateBusinessDates` 可复用规范化和事务校验逻辑，但不能直接当作大规模迁移器：其每用户完整历史写入可能超过事务限制，稳定重复行也会直接物理删除。新任务先 dry-run 估计规模；可容纳的用户一次事务完成，超限用户按受控 generation 分块准备，持续写入的变化通过日志追平，验证最终 revision 后原子切换 ready 标记。切换前不让半迁移投影进入线上读取。

大用户影子迁移的具体步骤为：捕获用户起始水位 S0 → 按稳定 ID 扫描并构建影子规范记录 → 扫描结束捕获 S1 → 按顺序应用 `(S0, S1]` 的变更后像与删除 → 核对影子记录和汇总 → 继续追平到 S2 → 在事务中比较当前 revision 等于 S2，再切换 activeGeneration。比较失败则继续追平，不在一个事务中重写全部历史。扫描期间落在游标之前的新增由日志补齐；影子实体保存版本，已经扫描到更新版本时不接受更早事件覆盖。

影子汇总按记录的“已有贡献 → 新贡献”更新，不把扫描结果和日志时长简单相加。迁移 checkpoint 必须包含已应用水位和 generation；恢复时重放幂等。日志可用窗口必须覆盖整个迁移耗时，超过窗口的任务中止并从新基线重建，不能跳过缺失变更后标记成功。

正常写入器在事务内读取 activeGeneration 并更新对应投影，不跨事务复用旧 generation；迁移切换与普通写入通过同一用户状态文档形成冲突保护。切换后所有新提交必须写当前 generation，避免刚切换就产生两套各自增长的统计。

每个任务保存 migrationId、用户、输入 revision、规则版本、checkpoint、输出校验结果和错误；重试幂等。重复身份合并保留 canonical ID 与旧 ID alias，并产生 delete/upsert 事件。不可判断的冲突留人工核对；终身勋章不在此迁移中自动批量撤销。

**步骤 4：部署索引与 readiness 标记。** 先读取线上已有索引和执行计划，再根据实际查询创建缺失索引，不根据仓库推断线上不存在索引。索引创建属于版本化部署迁移，完成构建后才能启用对应查询路径。

| 查询用途 | 建议逻辑索引/唯一标识 | 注意事项 |
| --- | --- | --- |
| 按用户完整旧快照 | `_openid, timestamp desc, _id asc` | 保留 V1 语义，混合时间类型先由兼容路径处理 |
| 按业务日期记录 | `_openid, businessDate, occurredAt, _id` | 实际字段名与排序以最终查询确定 |
| 用户变更日志 | owner + epoch + seq | 确定性事件 ID；服务端验证游标归属 |
| 日/月汇总 | 用户+业务日 / 用户+月份的唯一文档 ID | 不能先查询再随机 add 造成重复汇总 |
| 外部待处理任务 | status + nextAttemptAt + 稳定排序字段 | 租约领取仍需要事务条件校验 |
| 用户资料、成员关系 | 用户身份 / 团队+用户唯一标识 | 先报告重复文档，不能盲建唯一约束失败 |

用户级 `modelReady`、`projectionReady`、`changeLogEpoch` 等标记分别表达记录字段、汇总和增量日志是否完整；不能用一个业务日期版本代替全部迁移状态。就绪用户走新查询，未就绪用户走原兼容路径。团队报表有未就绪成员时按成员回退，不能把缺失汇总视为零分钟。

**步骤 5：引入日/月汇总，替换常用写入的全历史重算。** 新增按用户/日和用户/月的汇总投影。新增记录在事务内以稳定 ID 去重，读取目标日/月文档并更新 count、duration；同日第一条才增加活跃天数。重复提交不再次累计，删除最后一条需要减少活跃天数，日期更正同时更新旧日/月和新日/月。

迁移前后使用同一领域聚合函数进行影子对账：原始记录 → 期望日/月结果 → 实际投影。总次数、总时长和基础天数要求精确相等；允许的历史未知次数必须独立列出，不伪装成完整记录。

连续天数不能简单 `inc/max`，尤其补录缺口或删除后最长连续段可能变化。建议按日历日期汇总计算连续段，必要时维护用户活跃日期集合或区间；保留校准任务。若大用户连续统计改为异步，接口明确 `statsAsOfRevision`/计算中，不能把旧统计宣称与最新记录同版本。第一阶段宁可扫描按日投影，也不每次扫描包含正文的完整明细。

分页读取日投影仍需一致性保护：在事务外读取前后校验用户 revision，事务内再次比较后才提交计算结果；版本失配重读，或者返回明确的异步投影水位。保留当前 SDK 事务只使用 `doc` API 的兼容约束，不将集合分页查询直接移入事务，也不把事务外过期计算裸写回统计。

记录 ID 与 dedupe 判断改为直接文档查询或稳定身份索引；新记录不再为了幂等扫描所有历史。旧身份恢复继续走专门兼容路径，不把其匹配成本扩展到所有正常写入。事务保护不能为了减少请求被去掉。

**步骤 6：新增 V2 快照与增量协议。** 新增示例接口如下，名字可统一调整，响应语义必须保留：

```ts
beginRecordSnapshotV2() -> {
  success: true,
  data: { snapshotId, epoch, baseSeq, pageCursor, complete: false }
}

getRecordSnapshotPageV2({ snapshotId, pageCursor, limit }) -> {
  success: true,
  data: { records, nextPageCursor, complete, baseSeq, epoch }
}

getRecordChangesV2({ cursor, upperCursor?, limit }) -> {
  success: true,
  data: { changes, nextCursor, upperCursor, hasMore, epoch }
}
// 日志过期、epoch 变化或不合法游标：显式 RESET_REQUIRED / INVALID_CURSOR。
```

快照必须对应一致的 baseSeq。可先采用读取前后 revision 一致的完整构建，生成不可变快照 manifest 后分页返回；有并发修改则重试，预算耗尽返回可重试错误，保留客户端原缓存。大用户如果稳定构建不可行，再实现快照生成加变更追平方案；未证明其一致性前不要启用。snapshotId 必须绑定当前用户、有过期时间，页面游标是不可伪造或经过服务端验证的 opaque token。

客户端快照全部下载、校验后一次提交，随后从 baseSeq 消费增量。下载开始时捕获账号、本机 revision 和原已确认记录集合；提交前校验上下文，重放或合并下载期间的本机新增、删除与上传确认。新版写响应须携带确认的云端提交版本：高于 baseSeq 的记录不能因旧快照中缺失而被删除；无法判断版本时保守保留并安排下一轮校准。不能只保护 pending，因为下载期间它可能刚变为 synced。保留离线/待确认/ignored 本机记录，完整快照只能校准相应版本范围的已确认云端集合，不能整体清空资料库。下载中断不推进正式游标，不做缺失删除。

增量按单次捕获的 upperCursor 分页，过程中新增更高版本留到下一轮。每页数据及 nextCursor 同次持久化，成功后才取下一页；客户端保存实体版本或等效保护，重复事件幂等、旧事件不覆盖新状态。收到 `changes=[]` 时也只能按协议推进到已验证水位，不能擅自使用本机时间作为游标。

每一页都重新验证 epoch 和日志保留水位，或用有期限的同步租约固定所需日志窗口；读取中途发生日志清理导致窗口不再完整时，返回 `RESET_REQUIRED`，不能继续返回成功并推进游标。尤其当 seq 允许跳号时，不能靠观察缺号来发现分页丢日志。

delete 明确携带 cloudId、稳定别名及提交版本；客户端只删除匹配的已确认实体，不按日期/时间批量删除、不删除另一个本地未确认会话。日志/删除标记保留期限依据实际离线时长确定；超出期限的客户端必须重建快照，不返回伪装成功的空增量。没有必要在本批同时增加“离线删除”产品行为，仍可保留在线删除语义。

**步骤 7：优化本机存储和渲染。** 优先利用第二批 Repository 与 selectors 减少重复读取和 setData，再按基线决定是否启用历史分块。首页按业务日期索引读取最近三天，日历只读取 count/状态摘要，完整历史按月份分页；同一个记录不要同时以平面和分组形式重复送入模板。计时每秒更新只发送需要变化的字段。

物理分块按月份或固定容量组织，另设小型 manifest；待上传状态随所属记录持久化，并维护可重建任务索引。不能把所有未上传记录放在一个无限增长的键里。跨月变更、删除与同步游标使用 copy-on-write generation：先写新分块并校验，再切换 manifest，最后延迟清理旧 generation。重启只读取一个已提交 generation，游标包含在同一提交边界。

存储不足时停止迁移，保留旧 generation 和所有未上传数据；可按明确策略淘汰已确认且可恢复的历史缓存，不能把仅存本机的体验或 ignored 记录当成可删除缓存。缓存清理和业务删除必须是不同命令。

淘汰历史必须配套缓存覆盖范围、缺页标记和按月/日期范围的补载接口；增量只返回变化，无法恢复已经淘汰但没有变化的旧记录。范围补载结果携带范围、版本和分页完整性，最多校准明确完成的该范围，不能当作全库快照执行缺失删除。页面把未缓存显示为待加载，不能显示成零记录；待上传提醒仍覆盖所有日期，不随历史列表分页遗漏。

按提交的 changedIds/changedDates 精确失效 selector；同一批提交合并通知，隐藏页面仅标 dirty，显示时更新一次。真机测量确认：只更新上传状态不触发全历史排序，跨 02:00 日期与月份依然及时更新。

**步骤 8：让外部任务有界执行。** 延用第二批的持久任务，每次调度只创建/领取有限批次。消费者使用受控并发、外部限流、指数退避与抖动、最大尝试次数和人工处理状态；同用户/绑定/日期串行。数值依据对端限额和云函数时限配置，不把单次函数执行当永久工作进程。

任务超出执行预算前保存 checkpoint 并让租约到期可重领。一天失败的任务在第二天仍可见；业务日期变化不清除队列。只有收到有效确认才更新 ack，不因调用超时直接认定对端没有写入。保留第二批规定的迟到请求和重绑保护，增大并发不能破坏版本顺序。

**步骤 9：固定部署产物并建立观测。** 固定每个部署单元实际验证的 SDK 与运行时版本、提交锁文件、使用可重复安装。共享领域产物由构建生成且校验一致；生产包排除测试页面/调试资源时同时检查路由、分包及资源引用，避免移除仍被使用的页面。

日志记录 requestId、操作、版本、耗时、结果码与重试次数；不默认输出整段体验正文、完整资料或凭据。指标覆盖记录提交失败率、读写扫描量、delta/snapshot 回退率、迁移异常数、最老待同步任务年龄、租约冲突和客户端写入失败。查询索引、集合权限和迁移版本纳入发布清单。

**验证矩阵与发布门槛。** 下列用例既需隔离单元测试，也需在测试云环境验证真实 SDK、事务、分页及权限行为。

| 场景 | 必须满足的结果 |
| --- | --- |
| 01:59:59.999/02:00、跨月年闰日、不同设备时区 | 与第二批共享日期规则一致 |
| 手动补录、无可靠时间戳、无稳定身份的旧记录 | 日期和记录不被猜测性改写/合并 |
| 持续写入期间迁移、进程中断、同页重跑 | 幂等可续跑，最终完整校准，不丢新写入 |
| 并发新增/删除/体验修改/后台纠正 | 记录、revision、日志与必要投影原子一致 |
| 新老客户端同时使用 | V1 完整快照不变；V2 失败不误删本地 |
| 快照下载中断、增量重复乱序、旧账号迟到响应 | 缓存与游标不提前推进，不串账号 |
| 删除事件、日志过期、epoch 变化 | 删除精确；过期明确要求快照恢复 |
| 已删记录被另一设备迟到重传 | 持久删除凭证阻止复活；新会话身份仍可正常创建 |
| 按日/月汇总与团队统计 | 与原始事实对账一致，无重复累计 |
| 本机分块中断/写满/跨月操作 | manifest 原子切换，未上传与仅本机数据保留 |
| 外部失败跨日、请求超时、重新绑定 | 可追踪补偿，不误确认最新版本 |
| 100/1000/10000 条历史与最大团队 | 有测量报告；常用路径满足结构性成本目标 |

建议拆成六个 PR/发布单元：变更日志与写入覆盖；迁移器和报告；索引与影子汇总；V2 快照/增量；客户端 selector/分块；任务扩容与观测。每个单元有测试环境联调和独立开关，不一次切全量。

发布顺序：先部署向后兼容的记录写入与日志 → 创建并验证索引 → dry-run/导出 → 小范围迁移与影子对账 → 标记用户就绪 → 灰度启用新汇总和 V2 客户端 → 测量后扩大范围。旧客户端仍用 V1；旧数据与索引不在首次切换时删除。缺少对端归零/版本确认能力时，只阻止相关自动修正动作，任务保留需核对状态，不掩盖为同步成功。

**回滚方式。** 出现问题先关闭新读路径/V2 灰度或暂停迁移与消费者，保留兼容服务端的日志写入；不能回退到不写变更日志的旧写入器后继续使用原 epoch。确需这样回退时必须推进 epoch，并让 V2 客户端重新取快照。

汇总可以从原始事实重建；不要恢复整库旧导出覆盖迁移后新写入。字段恢复依据迁移清单、当前 revision 和变更日志逐项处理；已经有新修改的记录必须重算，不能盲目恢复旧值。客户端关闭分块只允许经过兼容导出/manifest 切换，不能恢复陈旧全量缓存。最终清理旧字段、旧 generation、重复行备份和 V1 接口需要独立清理发布，确认旧版本占比、日志保留期和恢复演练后再执行。

本批完成标准是：正确性矩阵通过、迁移报告无未解释差异、性能有基线对比、回滚演练通过、全量测试和真机/真实云环境联调有记录。只通过 mock 测试不能标记整批完成。
