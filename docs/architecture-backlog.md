# 架构待办

本文件收拢 2026-09-22 第二、三批尚未整体实施的方案，供后续独立改造评估；不是当前实现或部署完成声明。第一批存储、授权、审核和资料提交修复已有回归测试，运维门槛见 [maintenance-access.md](maintenance-access.md)。同步恢复已有后续实现，重新设计前先核对[当前自动恢复规则](2026-10-10-auto-sync-recovery.md)，不要恢复旧方案的“仅当天自动补传”限制。

## 单一写入入口与领域规则

- 保留 CommonJS 与现有部署单元，通过纯函数、Repository 和用例服务逐步收拢 `checkin.js`、资料写入及页面状态；旧接口先作为兼容 facade，不能双写两套事实。
- 共享日期、身份、规范化、统计、团队达标和勋章规则。云函数内使用打包副本或内部包，并以同一组 fixtures 和产物校验保证一致。
- 区分 `localUserId`、openid 与账号会话 generation；请求提交前核对账号和 revision。已绑定记录不能改归属，迟到响应不能写入新账号。
- 统一 envelope 可包含 schemaVersion、revision、ownerContext、checkinRecords、experienceRecords、extensions。按受控写入升级格式，保留未知字段、旧体验、原身份和同步标记；空间不足时继续旧格式。
- 本地 commit 的读取、校验、写入不跨 await，落盘成功才通知页面。网络结果提交时重新合并，不能覆盖请求期间新增数据。
- 上传任务持久化，内存 Map/Set 只负责互斥。区分未确认、待上传、上传中、已确认、失败、阻止和忽略，保持现行重试与账号隔离约定；不能凭缺少 cloudId 自动加入队列。
- 资料草稿与已确认资料分开；逐步引入白名单 patch 和 expectedProfileRevision，同字段冲突显式处理。旧资料键只作单向兼容镜像。
- 页面订阅必要投影，隐藏页标记 dirty，显示时一次更新；业务规则不直接刷新页面或弹提示。先迁移资料，再迁移记录写入、首页/历史、计时、团队和勋章。
- 正式勋章由已确认事实计算或验证，离线结果仅作待确认状态。保留终身成就与历史颁发时间，争议历史先报告，不在普通刷新中撤销。

## 持久外部同步

现有 `bijing_sync_errors`、同步版本、绑定归属和恢复游标已经承担部分职责；评估缺口后复用，不能直接再建平行任务系统。

- 以用户、bindingVersion、业务日期隔离任务，区分目标与确认的版本/时长、重试状态和租约。记录变更与 dirty 标记同事务提交，HTTP 在事务外执行。
- 回执只能确认发送版本；更新、重绑、迟到请求和超时均须重查或补偿。任务存在不等于远端已确认，超时也不等于未写入。
- 日期归零须有真实源记录/变更依据并核实对端零值协议；失败跨日保留。用户手动选择窗口、任务重试资格和对端历史范围分别约定。
- 调度按预算分批、保存 checkpoint、受控并发并处理限流；同用户/绑定/日期保持顺序。缺少对端版本或查询能力时保留待核对，不宣称恰好一次。

## 历史迁移与增量同步

这些工作依赖单写入口、全部写入的 revision 覆盖和可验证的变更日志，不能直接切换旧接口。

1. 量化 100、1000、10000 条个人历史及 1/10/50 人团队的读写字节、setData 大小、扫描量、p50/p95 和超时率；先建立基线，再定并发与耗时指标。
2. 记录、统计、revision 与变更后像/delete 事件同事务提交；覆盖旧接口、体验修改、迁移及运维写入。日志的 seq 可以跳号，完整性由 epoch、日志起点和保留水位保证。
3. 独立保留稳定身份的删除凭证，阻止长期离线设备重传复活已删除记录。日志清理不能同时遗忘删除身份；旧无身份记录仍走人工核对。
4. 迁移先报告、导出并明确目标，覆盖资料、统计和记录归属的用户并集。保留手动日期、原时间和体验，只按同用户稳定身份合并；冲突及无可靠日期不猜测处理。
5. 大用户采用影子 generation：记录起始水位、稳定 ID 扫描、追平变更日志、对账，再比较当前 revision 原子切换。checkpoint 包含已应用水位，普通写入事务读取 activeGeneration，避免切换后两份汇总各自增长。
6. 查询索引先核验实际环境，再建设并验证。记录就绪、汇总就绪和 changeLogEpoch 分别标记；未就绪用户走兼容路径，缺汇总不能视为零。
7. 日/月投影按记录贡献差量更新，重复提交不累计；跨日修改、删除最后一条、补录连续天数需正确校准。原始事实与投影对账，不能为了性能去掉事务保护。
8. V1 `getAllRecords` 继续返回完整一致快照。V2 单独提供有账号归属的 snapshotId、baseSeq、分页完整性、增量 upperCursor/nextCursor 和 epoch；日志过期返回 RESET_REQUIRED。
9. 客户端完整下载并校验后一次提交快照，合并下载期间的本机变化与较新云端确认。每页增量和游标同次落盘，失败不推进；delete 只匹配明确身份，不能按日期批量删除。
10. 快照/增量每页校验日志水位与 epoch；日志缺失不能返回成功空增量，也不能用本机时间充当游标。

## 本机容量与发布

- 先减少重复读写和全量 setData，再根据基线决定是否分块。按月/容量分块时，采用先写新块、校验、再切 manifest 的提交方式；同步游标属于同一提交边界。
- 空间不足不能删除仅本机、待上传或 ignored 记录。可恢复缓存淘汰必须记录覆盖范围、缺页状态并提供按范围补载；未缓存不等于零记录。
- 锁定各部署单元实际验证的 SDK/运行时，检查生成副本、查询索引、集合权限及迁移版本。日志保留 requestId、版本、耗时和结果码，避免正文和凭据。
- 按独立功能分批发布：共享规则/单写入口 → 写入日志 → 索引与迁移预览 → 小范围影子对账 → V2/新投影灰度 → 性能扩容。
- 验证跨 02:00/月底/闰日、双格式、存储满、账号切换、上传/删除交错、快照中断、重复/乱序增量、日志过期、持续写入迁移与回滚；需要真实 SDK 和真机验证。
- 回退先关闭新读路径或暂停迁移/消费者，保留日志和新写入。若退回不写日志的旧服务端，必须推进 epoch；不能整体恢复旧导出覆盖迁移后的数据。旧字段、旧 generation 和 V1 下线属于独立清理发布。
