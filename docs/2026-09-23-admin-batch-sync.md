# 必经批量同步与管控中心（2026-09-23）

> 2026-10-10 更新：新增遗漏日期覆盖进度、11:00 逾期管理员待办及全日期离线自动补传。下文关于“只恢复已有任务”“历史手动上传”“无需部署 adminManager / 客户端”的旧范围已由[自动恢复说明](2026-10-10-auto-sync-recovery.md)替代；本次必须核实新增日期索引，并部署三个云函数及小程序。

## 功能与口径

“我的”页连续点击版本号 7 次，通过独立 `adminManager.getAccess` 确认当前绑定学号在服务端管理员名单中后进入管控；直接打开页面和每次管理请求也会重新校验。

管理员只在 **`adminManager` 云函数环境变量 `ADMIN_STUDENT_NUMBERS`** 配置，多个学号用英文逗号分隔。本次指定完整名单为 `BJ2407159,BJ2302130`。配置忽略首尾空格及大小写；空名单、空条目、非法格式拒绝整份名单。旧 `ADMIN_OPENID`、`ADMIN_OPENIDS` 不再授权，无回退；旧维护入口的 `MAINTENANCE_ADMIN_OPENIDS` 保持独立。

身份取自 SDK 的真实 OpenID，再读取其当前绑定。客户端传入学号、昵称、isAdmin 和缓存均不能授予权限。每个学号只能绑定一个微信账号；管理员学号若有历史重复绑定，先拒绝授权，待相关账号自行解绑到只剩唯一绑定后恢复。现有唯一绑定不要求重新绑定。

`teamManager` 和 `bijingSync` 每次管理请求通过 `cloud.callFunction` 调用 `adminManager.getAccess`，不缓存授权。微信平台的嵌套调用不保证保留原始 OpenID：业务函数使用自己收到的真实 SDK 身份，在仅服务端可访问的 `bijing_bindings` 写入 30 秒有效的一次性凭据。`adminManager.getAccess` 在事务中校验并消费凭据，再检查当前学号绑定；`expectedOpenid` 只核对凭据身份，单独传入它或伪造 SOURCE 都不能授权。有真实 SDK 身份时还须与凭据一致。凭据不会返回客户端，请求结束会清理，重放或过期无效。记录查询和提醒接口仍要求直接 SDK 身份。中央校验故障或身份不一致拒绝当前管理操作。

管理员配置与换账号：

1. 首次升级先创建 `bijing_bindings`，设为仅服务端可读写 `{"read":false,"write":false}`；`users` 使用 `{"read":"doc._openid == auth.openid","write":false}`，保留本人读取并禁止客户端直接写入（当前资料修改走云函数白名单）。完整部署三个必需云函数：`bijingSync`（含 `bindings.js`）、`meditationManager`（避免旧重复资料遮住当前绑定）、`adminManager`（含 `studentAuth.js`、`delegation.js`）。逐个部署并等待 `Active` 后才做下一次更新。`teamManager` 同步更新 `maintenanceAuth.js` 的一次性凭据逻辑。
2. 在「云函数 → adminManager → 配置 → 环境变量」设置完整 `ADMIN_STUDENT_NUMBERS`。之后增加或移除管理员只改此处，不必同步其他函数。删除变量或设为空串都关闭管控授权。
3. 原账号在「我 → 必经之路 → 解绑」确认，随后新账号绑定同一学号。解绑保留静坐记录和同步归档，立即撤销旧账号的学号授权；历史静坐记录仍属于原微信账号，不随绑定转移。
4. 已绑定账号不能直接覆盖成另一个学号；必须先解绑。并发绑定通过学号锁、账号锁和用户文档的事务一起提交。新绑定带版本号，旧页面不能解绑后来的新绑定；失败不会只写入一半。

管理员身份通过后，各 tab 独立加载：同步使用 `bijingSync`，记录查询使用 `adminManager`，团长与操作记录使用 `teamManager`。某个业务服务未更新时只影响对应 tab，页面框架与其他 tab 仍可打开；每次管理数据读取和修改都由 `adminManager` 统一鉴权，中央鉴权不可用时相应管理请求均拒绝执行。旧维护操作和原生定时器继续使用独立授权规则，不受管控名单变更影响。

- **必经同步**：默认展示最近 7 个已结束静坐日（含第 7 天）的执行记录；切换到“所选日期”后，可查看最近 30 个已结束静坐日内该日期的执行情况，与手动补同步的可选日期一致。记录按静坐日期降序、同日执行时间降序排列，每页最多 50 条，执行历史支持“加载更多”；刷新会重新读取已加载的页数，保留已展开的历史范围。展示成功/失败/跳过人数、开始/结束时间与耗时，并支持分页查看逐学号错误。主同步按钮始终针对所选日期：该日期已有可续跑任务时继续原任务，否则发起所选日期的手动同步；其他日期的活动任务不会抢占这个操作。超过 30 天的既有错误修复仍可通过独立活动状态继续处理。
- **最终核对与待修复错误**：每日 03:00–10:00 每小时整点核对前一个静坐日，并继续历史日期已登记的修复任务。已识别到用户的上传、读取、回查或修复失败写入 `bijing_sync_errors`；尚未枚举到用户就中断的整轮任务保留在 `bijing_sync_runs`，后续调度重新核对源数据。只有实际落库结果与当前源总量一致才清除待办。管控页可查看、手动重试；每次打开或从后台返回小程序时，`adminManager.getSyncAlert` 合并同步待办与待处理/处理中的用户反馈，指定管理员的底部“我”图标显示红点。前台停留、页面切换、刷新与修复完成不额外查询，两类待办清空后下次打开小程序移除红点。
- **记录查询**：输入完整昵称（忽略输入首尾空格），选择静坐日期，查看该用户已上传到小程序云端的静坐次数、总分钟数和逐条时间、时长、来源。重名账号按学号和账号标识选择，不合并不同用户的记录。查询默认当日，可选择历史日期，不受补同步的最近 30 日限制；未上传的本机记录不在查询范围内。
- **团队团长**：从团队当前成员中选新团长，旧团长保留普通成员身份；同步更新团长资料、成员关系与人数。若另一管理员先完成变更，要求刷新后再操作。旧团长此前分享的邀请会失效。
- **操作记录**：记录团长变更的操作者、前后团长、团队和时间，与变更在同一事务提交。手动同步的操作者保存在该次同步运行记录的 `operator` 字段。

静坐日延续现有北京时间 02:00 切日：例如 9 月 23 日 02:00 同步 **9 月 22 日 02:00 至 9 月 23 日 02:00** 的数据。手动补录使用显式记录日期。原按个人绑定学号的单条同步与最近七日补同步保留，不改为全员操作。

## 个人记录查询接口

两个新接口均由 `adminManager` 提供，参数直接放在事件顶层，每次请求先检查真实调用者的唯一有效绑定学号是否在服务端管理员名单内；未获得学号管理员权限的普通用户、旧维护身份和伪造客户端身份均返回 `FORBIDDEN`，不读取目标用户的个人记录；身份校验只读取绑定所需资料。

| type | 参数 | data 返回值 |
| --- | --- | --- |
| `adminSearchUsers` | `nickname`，可选 `cursor` | `users: [{ openid, nickname, studentNumber }]`、`nextCursor`；完整昵称精确匹配，每页最多 50 人，未绑定学号为空字符串 |
| `adminGetDayRecords` | `openid`、`recordDate: YYYY-MM-DD` | `user`、`recordDate`、`records: [{ _id, date, timestamp, duration, source }]`、`totalCount`、`totalDuration` |

`timestamp` 为毫秒数或 `null`，`source` 为 `manual`、`timer` 或 `unknown`，时长单位为分钟。当天记录在服务端分页读取、按既有记录身份去重后汇总，不以数据库单页上限截断；读取前后核对 `meditation_locks` 中的用户记录版本，遇到并发变更最多重读三轮，持续变化则提示重试。旧环境缺少该辅助集合时兼容只读查询，不自动创建集合。没有有效时间戳的旧记录保留日期且不补造时间。不存在的昵称与“用户存在但当天无记录”在页面分别提示。查询失败保留错误供重试，切换昵称、日期、用户或离开页面后，过期响应不回填旧记录。

在已完成学号鉴权升级的环境中，仅更新记录查询模块时：更新 `adminManager` 云函数并保留当前学号管理员配置，确认 `users` 的 `nickName` 升序、`_id` 升序复合索引以及下列既有用户/记录索引，再发布小程序；无需另增集合或修改已有安全规则。尚未升级中央鉴权的环境，先按前文首次升级步骤完成集合、安全规则和对应云函数部署。

管控页分页与调度器使用不同的查询索引；升级前按下表同时核验日期内任务索引、跨日期状态索引和错误日期索引。已有执行历史继续保留。

## 执行机制

静坐日按北京时间 02:00 至次日 02:00 计算。每日全量上传与新的源核对针对最近一个已结束静坐日；已经登记的历史失败不会因跨日而被丢弃，也不受最近七天或三十天的手动日期范围限制。

仅保留两个原生定时器，时间均为北京时间：

- `dailySyncBijing = 0 0 2 * * * *`：02:00 建立刚结束日期的全量上传。在同一次调用内连续分批读取并上传；不保存逐批上传游标或 `bijing_sync_items`，整轮结束保存 `uploadSummary` 并置为 `uploaded`。上传中已知的逐人读取或上传失败进入错误表。`uploaded` 只是上传阶段结束，不代表实际落库已核对。
- `checkBijingSync = 0 0 3-10 * * * *`：03:00–10:00 每小时整点推进源核对与修复。每小时用独立 `cycleKey` 去重；上一轮仍在运行则继续 checkpoint，已经终结则重新从 `users` 和静坐记录读取源数据。即使 02:00 完全漏跑或只传了一部分，也会核对完整目标日期。

同一个整点还通过 `pendingRepairs.js` 扫描历史错误、运行中任务、任务级失败和已上传但未核对的任务，按日期继续修复。历史日期和最新目标日期共用持久化轮转游标，执行每个日期前先推进游标，避免一个持续超时的日期占满每次调用。运行中的核对从 checkpoint 继续；上传中断且没有上传游标的任务转为源核对；状态为 `uploaded`、仍是该日期最新全量运行且尚未被独立源核对接管的任务，也会跨日转为核对，覆盖 02:00 已收到上传确认但后续整点核对一直未建立的情况。已有源核对接管的旧上传不重跑。未枚举到用户的任务级故障由运行记录恢复，不伪造逐人错误。扫描只恢复已有待办，不凭空补建最近七天的全量任务。

01:00、03:00 前及 10 点之后的其他时段不新建核对周期，也不增加 `resumeBijingBatches` 定时器。最后一个整点仍失败或随后才登记的历史变更，保留到下一个允许的整点，包括次日 03:00 起继续；管理员可提前手动处理。一次调用或一次运行的重试预算不会把日期永久排除，错误在恢复前持续保留。

### 记录变更与失败持久化

`meditationManager/syncQueue.js` 将已绑定用户的历史新增、补录、离线补传或删除产生的待办，与记录和统计一起写入事务。待办按规范化学号、日期定位，保存真实账号、绑定资料及重新汇总后的总分钟。事务失败时整笔记录变更失败，不能返回“记录已保存”却没有修复意图；客户端保留原记录身份重试。重复成功确认复用原记录，不重复累计统计。历史幂等补确认通过记录或删除凭据上的 `bijingSyncQueued: true` 标记首次登记：原来尚未登记的旧确认补建待办，已经处理过的回放不重建任务。该标记表示已登记，不代表必经已同步成功。

历史记录云端确认后，现有客户端仍立即调用 `syncRecordedDate` 或 `syncDeletedDate`。客户端退出或保存回包丢失，不会丢掉已提交的服务端待办。离线记录只有成功补传云端后才进入必经同步；当天的离线补传仍走次日日结，历史记录的上传选择与确认流程保持不变。

`bijingSync/syncFailures.js` 在个人同步向必经发请求前登记待办，失败保留诊断；上传接口返回成功仍需实际回查。旧个人接口只确认上传，若迟到成功时待办已被其他请求清除，会在绑定仍匹配时补回新的待核对记录，不覆盖现有待办或增加失败次数。批量任务也持久化已知的源读取、上传、回查和修复失败。读取失败标记为 `source_read_failed`，查询故障表示“尚未核对”，都不能当作远端缺失或实际零分钟；没有读到远端状态时 `exists`、`actualDurationMinutes` 使用 `null`。

每次源记录变更生成新的 `queueVersion`。自动和个人同步清除或更新待办时，在事务内比较捕获的版本及归属；旧请求的迟到成功不能删除后来新增、补录或删除产生的新待办。修复前重新读取当前源总量并核对唯一绑定，不使用旧错误快照直接覆盖。绑定异常保留问题供核查，不能把旧账号记录写给另一个账号。

### 修复与清零

核对、差异上传、再次核对在同次调用内连续推进。`POST /api/openapi/meditation/records/query` 按学号、日期返回 `exists` 和 `durationMinutes`；响应缺项、数量或身份不符、网络及数据库异常均保留待办，不能报告成功。批量任务标记成功及清错前会再次读取当前源总量，只有它与刚查询的实际落库一致才清除对应版本的错误；不能只依赖早先捕获的总量或当前错误行是否存在。若新待办已被另一个请求处理并清除，迟到批请求仍会登记 `source_changed` 待核对并重新读取源数据，不将旧快照当作新的期望总量。

正分钟通过批量接口覆盖当天总量。对于带有 `zeroEligible: true` 或已确认本人真实源记录、记录变更、同步依据，且归属仍匹配的日期，重新读取确认源总量为 0 时，使用既有单条 `POST /api/openapi/meditation/records` 发送数值 `durationMinutes: 0`，再回查确认清除；批量接口仍只接受正整数。`zeroEligible` 只能来自本人真实源或变更；仅有 `binding_conflict`、`source_read_failed` 等错误并不授予清零资格，不会仅因一个绑定用户从未有记录就清除必经的数据。无需为本次修复修改 `bijing-data` 接口，部署前仍需核实目标环境已具备既有单条清零和查询能力。

`BATCH_SIZE=100` 是上传、查询及正数修复的 HTTP 批容量；`CHUNK_SIZE=20` 是核对修复保存明细、错误与游标的单次 checkpoint 行数上限。源用户与历史记录按 `_id` 分页，无记录或读取失败源行也推进游标。任务按日期领取 120 秒租约，读取、请求与 checkpoint 间按需续租；所有请求及提交检查 token。每位用户源读取有独立 20 秒预算，批量 HTTP 请求独立超时 15 秒，单次调用可连续处理多个批次。源扫描、错误源读取与修复前重读完成至少一人后，若累计达到 5 秒，会提前结束当前页并保留后续页；同步标记耗时达到 5 秒也提前保存已完成子组的 checkpoint。单条清零每次处理一人便保存进度，避免多次慢请求一直重复同一段。5 秒是主动保存进度的软预算，不替代单用户读取预算或平台时限。

代码不把整次云函数调用固定限制为 60 秒，但平台执行时限独立生效。中断保留运行与已提交的 checkpoint，下一允许整点恢复；上传阶段没有逐批游标时通过完整源核对补齐。[2026-09-23 上线记录](2026-09-23-production-rollout.md) 的 60 秒是历史配置，本次未核实或修改实时云端值。上线前按[云函数配置文档](https://docs.cloudbase.net/cloud-function/function-configuration/config)核实执行时限，并实测全量读取、上传、核对及积压修复耗时；租约可续租不代表平台不会终止函数。按[数据库事务文档](https://docs.cloudbase.net/database/transaction)，单事务最多 100 次操作、执行时限 30 秒，因此不能把 100 条 HTTP 批容量直接当作单事务写入容量。

管理员仍可按日期继续任务、重试错误或发起最近三十日的全量同步；超过三十天的既有错误可继续修复。每次运行的“用时”包含其中断等待时间，`attempts` 是日期执行轮次，不是逐项 HTTP 次数。正确性与吞吐需分别验收：本地 mock 通过不能代替真实触发器、数据库索引和大批量耗时验证。

## 数据与部署顺序

**本次尚未部署或修改云端配置。** 以下步骤针对已完成学号鉴权及批量接口升级的环境；首次安装仍须先完成前文绑定注册表、中央鉴权及原批量接口准备。历史上线记录不代表本次变更已发布。

## 上线验收

先在测试环境执行一轮包含正常学号、停用学号、无记录用户的同步，核对源核对运行的逐项结果与必经实际记录一致，上传摘要可结合接收端审计检查。重复同步同日时应覆盖总分钟，不能累加。验证转移团长后旧团长仍在团队、审计记录存在。

验证管理员默认历史只显示最近 7 个已结束静坐日，选择第 8 至第 30 个已结束静坐日时，可以查看该日执行记录并手动同步。历史超过 50 条时能够加载更多，刷新后保留已加载的页数，切换日期或展示范围后重新开始分页。存在其他日期的活动任务时，主按钮仍同步当前所选日期；所选日期已有可续跑任务时继续同一运行。手动同步完成后能在所选日期查看结果和核对明细，自动上传记录只提供上传汇总，逐人核对结果查看该日的独立核对运行。

验证上传、查询和差异重试真实按最多 100 条发送 HTTP 请求。02:00 同一次调用连续上传全部用户，确认上传期间不写 `items` 或逐批游标，已知逐人失败写入 `errors`，整轮最后保存 `uploadSummary` 并置为 `uploaded`。强制在上传中途结束调用，确认没有额外定时器或管理页轮询重新上传；再分别验证 02:00 完全漏跑、部分上传、全部上传三种情况下，03:00 起的源核对都从 `users` 独立扫描完整目标日源数据，核对范围和最终结果不依赖上传摘要。

验证每轮源核对按最多 20 个已扫描源用户行保存 checkpoint，快路径 100 行可分 5 个事务，包含无记录及读取失败源行时游标仍正确推进；慢读取或标记达到 5 秒软预算时可提前保存更小页/子组，不能将短页误认为全量结束；单条零清除逐人保存游标。同一次调用连续处理后续批次及核对周期各阶段。确认逐用户源读取各有 20 秒预算；读取、标记及中间 checkpoint 按需要续租，中间保留同一 token、最后释放。核对修复在租约繁忙、任务运行错误或没有进度时退出；已登记历史任务可在后续允许整点跨日继续。模拟核对 HTTP 已完成但只提交部分 checkpoint 时中断执行，确认下一允许整点会继续仍在运行的任务，从已提交源游标恢复；若上一轮已终结，下一小时重新读取源数据核对。管理员仍可手动继续或按日期重跑；验证核对 HTTP 前的目标日期与 token 校验及 checkpoint token 校验。

验证学号权限与换绑：两个账号并发绑定同一学号只能一个成功；已绑定账号切换学号须先解绑。原账号解绑后，下一次管理请求被拒绝，新账号可绑定该学号并按当前管理员名单获得权限；原账号的静坐记录仍保留在原账号。历史重复绑定的管理员学号在仍有多个有效账号时均不能授权，不自动挑选保留者。真实小程序跨云函数调用还须验证 SDK 身份传递，不能用本地模拟调用代替。

验证上传已落库但响应丢失时，首次核对直接成功，先前因响应丢失登记的待办应在核对后清除；上传未落库或远端分钟数不符时，首次核对写入差异，重试后实际查询一致才删除。查询故障不得清空错误或报告成功。确认仅管理员看到“我”红点，每次打开或从后台返回小程序只查询一次，前台停留与页面操作不额外查询；待修复列表恢复清空后，下次打开小程序时红点消失。进入后台应取消未完成的提醒请求，忽略过期响应；请求失败或超过 10 秒时清除红点，等下次打开再查询。

分别观察两个真实原生定时器的 SDK `SOURCE=wx_trigger` 与 `TriggerName`：02:00 上传最终为 `uploaded`；03:00–10:00 每小时整点推进当前日期核对和历史待办。验证同小时重复投递不重建同轮任务、并发调用不重复消费；01:00 等非允许时段不新建周期，云端没有 `resumeBijingBatches` 或重复规则。最后整点故障后跨日保留待办，次日允许整点自动继续；同时验证 02:00 已上传但整日未建立核对的最新全量任务会跨日补核对，而已被源核对接管的旧上传不会重跑；模拟历史日期反复超时，验证轮转游标仍让其他日期及最新目标日获得执行机会。

验证历史新增、离线补传和删除的记录/统计/待办同事务提交，客户端不发第二次同步请求也能由定时器接续；当日离线记录仍走次日日结。模拟旧请求确认与新记录变更并发，确认旧 `queueVersion` 不能清除新待办。删除最后一条后自动调用既有单条零清除接口并回查，不向批量接口发送 0，也不清除从未有源或同步依据的日期；单纯绑定冲突或源读取错误不能授予清零资格。模拟新待办已被另一个请求清除后旧批请求才返回，验证清错前的源重读及 `source_changed` 待核对仍可发现变化。绑定变更、源读取失败与回查失败均保留可诊断待办。

只有最近真实运行日志、实际触发器、平台时限和必经回查共同通过，才可认为自动同步已验收。页面“自动同步已启用”只说明环境变量配置，不能替代上述核验。
