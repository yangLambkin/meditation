# 首次倒计时结束铃声修复

反馈场景：iPhone 真机始终停留在计时页，起坐正常；第一次倒计时结束无铃声，第二次手动结束和第三次倒计时结束正常。

## 排查结论

自然结束和手动结束共用完成与提醒路径。收坐资源可以完整解码，开头没有明显静音。模拟原生事件复现了两个播放器缺口：

- 起坐与收坐复用原生实例，旧音源的延迟事件可能派发到新监听，提前确认尚未播放的收坐提醒。
- `Ended` 原先直接代表成功；从未启动或只收到 `Play`、时间仍为零的异常结束，也会撤销待提醒和故障检测。

首次解码较慢同样可能触发原先统一的 2.5 秒超时。上述是已复现的代码风险，尚不能仅凭模拟测试确定这台 iPhone 当时的原生事件顺序。

## 修复

- 每段新提示音使用独立原生播放器，只有同一段的暂停/继续复用实例。
- 用户开始静坐时静默预加载收坐资源；到点直接使用准备好的实例，避免重复设置音源。预加载失败不影响起坐或消耗实际播放重试。
- 区分加载与播放：支持 `Canplay` 的客户端加载最多等待 10 秒，就绪后按 2.5 秒检查启动和持续进度；最多重建一次，仍失败沿用震动、提示和保留待提醒的处理。
- 结束确认要求已收到本次 `Play`；支持进度的客户端还必须有本请求的可信播放位置。保留结束前时间归零、暂停恢复和旧客户端兼容。
- 前台恢复先处理倒计时，再刷新底部导航；导航异常不能冻结计时。
- `timerDiagnostics` 增加播放请求、首次可信进度、完成结果，沿用最多 200 条的本机诊断限制，不逐帧写日志。

## 验证

自动化覆盖首次自然结束 → 手动结束 → 再次自然结束、有/无引导、一次提醒与一次保存、旧事件干扰、6 秒冷加载、永久卡住、有界重试、预加载失败及清理、暂停/继续。

运行音频专项：

```sh
node --test tests/cuePlayer.test.js tests/timerColdStart.test.js tests/timerEndReminder.test.js tests/timerExitAudio.test.js
```

iPhone 验收需使用更新后的构建，从重新打开小程序开始，保持计时页前台，按上述三次顺序测试；每次确认起坐、收坐只播放一次，记录时长正确。再测试暂停/继续和有引导音频。自动化无法验证手机扬声器是否实际出声，真机结果应单独记录。
